# 실습 4 — 관리자라면 다른 회사 발주도 승인할 수 있나요?

실습 3까지 마친 뒤 진행합니다. 이번에는 회사 경계 결함 실습 공간을 선택합니다.
이 공간은 본 실습과 DB·세션이 별개이고, 역할·상태 검사는 준비되어 있습니다.
앞에서 만든 코드를 복사하거나 되돌릴 필요는 없습니다.

> 관리자는 자기 회사의 승인 대기 발주만 승인할 수 있습니다.

## 결함 관찰

1. 회사 경계 결함 실습 공간을 초기화합니다.
2. A회사 관리자로 접속하고 발주 메뉴를 엽니다.
3. A회사 목록에 B회사 2001번이 표시되지 않는지 확인합니다.
4. 회사 경계 확인에서 B회사 발주 승인 요청 보내기를 누릅니다.
5. 실제 응답 200과 본문을 확인합니다.
6. B회사 관리자로 전환하고 메뉴·2001번 상세를 엽니다.
7. 승인 완료 상태와 승인 처리 횟수 1을 확인합니다.

B회사 발주는 A회사 목록에 표시되지 않습니다. 준비된 장치는 대상 ID로 서버에 직접 요청합니다.
목록을 숨기는 것과 서버가 승인을 막는 것은 별개입니다. 지금은 정해진 회사 기준을 위반한 결과입니다.

## 수정 전에 흐름 추적

```text
AGENTS.md와 README.md를 읽고 회사 경계 결함 실습의 원인을 조사하세요.
요청 전송 → 사용자 확인 → 발주 조회 → 역할·상태 검사 → 저장 순서로 정리하세요.
서버가 확인한 사용자 회사가 발주 조회 조건에 쓰이는지 확인하세요.
각 단계에서 회사 값이 어디에서 오는지도 함께 표시하세요.
각 단계의 파일·함수·검색어를 한 줄로 적고, 누락된 조건과 최소 수정 위치를 알려 주세요.
관찰 결과와 코드 근거를 구분하고, 찾지 못한 곳은 미확인으로 표시하세요.
코드 조사만 하고 파일 수정이나 명령 실행은 하지 마세요.
```

AI가 안내한 위치에서 다음을 직접 확인합니다.

- 사용자의 회사는 서버 세션에서 나오는가?
- 승인할 발주를 찾을 때 그 회사로 범위를 제한하는가?
- 조회한 발주의 회사와 사용자가 접근할 수 있는 회사는 어떻게 다른가?

원인을 설명한 다음에만 수정 요청을 실행합니다.

```text
AGENTS.md와 실제 조회 코드를 읽고 회사 범위 누락을 최소 수정하세요.
변경할 파일과 이유를 먼저 알리세요.

- 서버 세션에서 확인한 사용자 회사와 발주 ID로 승인 대상을 찾으세요.
- 요청값이나 조회된 발주의 회사로 접근을 허용하지 마세요.
- 다른 회사와 없는 발주는 모두 404와 '발주를 찾을 수 없습니다.'로 응답하세요.
- 거부 응답에는 발주 내용을 넣지 않고, 대상 상태·처리 횟수를 유지하세요.
- 자기 회사 정상 승인과 기존 역할·상태 검사를 유지하세요.

수정 범위는 AGENTS.md의 실습 4입니다. 승인 대상 조회의 회사 조건만 고치세요.
변경 파일·실행 결과·미확인 항목을 짧게 보고하세요.
```

## 수정 후 재확인

결함 공간을 초기화하고 A회사 관리자로 같은 요청을 다시 보냅니다.

| 행동 | 확인할 결과 |
|---|---|
| A관리자가 B회사 2001번 승인 요청 | 404, '발주를 찾을 수 없습니다.', 대상 품명·상태 등 데이터 없음 |
| B관리자로 전환해 2001번 상세 조회 | 승인 대기, 승인 처리 횟수 0 |
| A관리자로 전환해 메뉴·1001번 상세에서 직접 승인 요청 | 200, 승인 완료, 승인 처리 횟수 1 |
| 같은 1001번에 새 승인 요청 | 409, 처리 횟수 1 유지 |
| A조회 담당자로 전환해 메뉴·1001번 상세에서 직접 승인 요청 | 403, 상세 조회는 계속 가능 |

## AI 검증과 완료

실행 전 예상, 실제로 본 결과, 결과를 설명하는 코드 또는 업무 기준을 세 줄로 적습니다.
실제 행동과 수정 전후 응답·상태·횟수를 포함하며 미확인은 그대로 적습니다.

먼저 **회사 경계 결함 실습**의 수정 결과를 검증합니다. 아래의 `[내 기록]`에 이번 공간에서
직접 관찰한 결과를 넣습니다.

```text
AGENTS.md를 읽고 회사 경계 결함 실습의 수정과 제 기록을 검증해 주세요.
실제 변경을 _starter/와 비교하고 제공 파일의 변경 여부를 검사하세요.
타회사·없는 발주 404, 거부 후 상태와 횟수 유지, 자기 회사 정상 승인을 확인하세요.
기존 역할·상태 거부도 확인하세요. 제 기록과 코드가 다르면 근거와 다음 행동을 알려 주세요.
결함 공간만 검토하고, 파일 수정 없이 변경 범위·실행 결과·미확인 항목을 짧게 보고하세요.

[내 기록]
```

독자는 **수정이 회사 조건에 한정됐는지, 거부 뒤 데이터가 유지됐는지, 정상 승인은 가능한지**를
확인합니다. 실행하지 않은 사례는 `Not Run`으로 남기고, 코드 확인만으로 통과시키지 않습니다.

이어서 **본 실습의 회사 차단이 유지되는지** 확인합니다. 두 공간은 승인 처리 코드와 DB가
다르므로 별도 검증이 필요합니다. 회귀 검증은 앞에서 되던 동작이 변경 후에도 유지되는지
다시 확인하는 것입니다. 본 실습에는 B회사 요청 버튼이 없어 AI에게 로컬 API 요청을 맡깁니다.

```text
AGENTS.md를 읽고 본 실습의 회사 차단을 로컬 API로 다시 확인하세요.
현재 실행 주소와 이 공간의 사용자·API를 먼저 조사하세요.
B회사 관리자로 2001번의 상태·횟수를 조회하세요.
A회사 관리자 세션으로 같은 발주에 승인 요청을 보내세요.
404와 '발주를 찾을 수 없습니다.'가 반환되고 발주 내용은 노출되지 않아야 합니다.
B회사 관리자로 다시 조회해 상태·횟수가 요청 전과 같은지 확인하세요.
공간·사용자·발주 ID·실제 응답·재조회 결과를 보고하고 미실행은 Not Run으로 표시하세요.
본 실습만 검증하며 파일·검사 기준은 수정하지 마세요.
```

독자는 **본 실습·A회사 관리자·2001번 요청·404 응답**인지 확인합니다.
B회사 관리자의 요청 전후 재조회 값까지 같아야 데이터 유지도 확인한 것입니다.

AI 피드백 뒤 근거 한 곳을 직접 확인하고 자신의 설명을 보완합니다.
서버가 확인한 회사가 어디에서 조회 범위를 제한하는지 설명하고 위 결과를 재현하면 완료입니다.

### 완료한 규칙을 조합해 확인합니다

다음 표는 **4.4까지 완료한 본 실습과 회사 조건을 수정한 결함 공간**의 승인 API 기대 결과입니다.
각 행은 초기 데이터에서 따로
시작하는 사례이며, 초기화 후에는 해당 공간에서 사용자를 다시 선택합니다.

| 접속 사용자 | 대상 발주·회사·시작 상태 | 기대 응답 | 처리 후 확인 |
|---|---|---:|---|
| 미접속 | 1001·A·승인 대기 | `401` | 상태·횟수 유지 |
| A회사 관리자 | 1001·A·승인 대기 | `200` | 승인 완료·횟수 1 |
| A회사 관리자 | 1002·A·승인 완료 | `409` | 승인 완료·횟수 1 유지 |
| A회사 조회 담당자 | 1001·A·승인 대기 | `403` | 승인 대기·횟수 0 유지 |
| A회사 조회 담당자 | 1002·A·승인 완료 | `403` | 승인 완료·횟수 1 유지 |
| A회사 관리자 | 2001·B·승인 대기 | `404` | 대상 내용 비노출·상태와 횟수 유지 |
| A회사 조회 담당자 | 2001·B·승인 대기 | `404` | 대상 내용 비노출·상태와 횟수 유지 |
| A회사 관리자 | 9999·없는 발주 | `404` | '발주를 찾을 수 없습니다.'·데이터 변화 없음 |
| A회사 조회 담당자 | 9999·없는 발주 | `404` | '발주를 찾을 수 없습니다.'·데이터 변화 없음 |
| B회사 관리자 | 2001·B·승인 대기 | `200` | 승인 완료·횟수 1 |

이 장의 흐름은 **접속 확인 → 자기 회사 발주 조회 → 역할 검사 → 상태 검사 → 저장**입니다.
따라서 조회 담당자가 자기 회사의 승인 완료 발주에 요청해도 상태 검사 전에 `403`으로 멈춥니다.
타회사·없는 발주는 역할 검사 전에 같은 `404`와 '발주를 찾을 수 없습니다.'로 응답합니다.
검사 순서는 이 키트의 기준이며, 모든 시스템에서 같은 응답을 우선한다는 뜻은 아닙니다.

표는 기대 결과를 정리한 것이며 전부 실행했다는 기록은 아닙니다. 추가 검증은 선택입니다.
화면에서 확인할 수 있는 사례는 **승인 요청 직접 보내기**를 사용합니다. 미접속·없는 ID와
본 실습의 타회사 요청은 화면 버튼으로 지정하기 어려우므로 AI에게 해당 공간의 로컬 API로
확인하게 합니다. 미접속 사례는 세션 없이, 나머지는 표의 사용자로 접속한 세션으로 요청합니다.
다른 회사의 상태·횟수는 그 회사 사용자로 다시 조회합니다. 응답만 보고 불변을 단정하지 않습니다.
AI에게 공간·사용자·대상 ID·실제 응답·재조회 결과를 표와 대조하게 하고, 실행하지 못한 사례는
`Not Run`으로 남깁니다. 본 실습에서 검사 순서가 다르면 차이와 수정 위치를 먼저 보고받습니다.

### 선택 실행: 승인 API를 한 번에 검증합니다

4.4까지 구현한 뒤에는 다음 명령으로 위 표의 10개 사례를 두 공간에서 각각 확인할 수 있습니다.
각 공간에서 쿼리와 요청 본문의 `corp_id`를 B회사로 보내도 타회사 접근이 차단되는지 2개씩
추가해, 모두 24개 사례를 실행합니다. 회사·역할은 계속 서버 세션을 기준으로 판단해야 합니다.

```powershell
.\.venv\Scripts\python.exe .\verify_business_rules.py
```

이 도구는 현재 코드를 임시 폴더로 복사해 별도 서버·DB·세션을 사용합니다. 각 사례는
초기 데이터에서 시작하며, 현재 실습 데이터와 실행 중인 서버는 유지합니다. 실행 후에는
이번 검증이 만든 임시 서버와 파일을 정리합니다. 처음 코드나 중간 단계에서는 완성 기준을
만족하지 않아 실패할 수 있으므로, 4.4 완료 후 선택해서 실행하세요.

`RESULT`에서 `Pass=24 Fail=0 Not Run=0`과 종료 코드 `0`을 확인하면 전체 통과입니다.
`FAIL`이면 첫 실패 행의 공간·사용자·발주·기대값·실제값을 비교하세요. 잘못된 응답 형식도 실패로 표시합니다.
`NOT RUN`이면 표시된 환경·DB 조회·서버 오류부터 확인합니다. 가상환경의 Python으로 실행했는지도 확인하세요.
종료 코드는 통과 `0`, 기준 실패 `1`, 환경·미실행 문제 `2`입니다. 서버 준비·정리 오류가 있으면 통과로 보지 않습니다.
문제를 고친 뒤 같은 명령을 다시 실행합니다. 검사 기준은 유지하고, 화면 버튼 제한은 직접 확인합니다.
동시 요청과 저장 실패 시험은 이번 자동 검증 범위에 포함되지 않습니다.
