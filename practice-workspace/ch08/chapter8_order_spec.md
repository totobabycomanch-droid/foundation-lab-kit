# Chapter 8 발주 업무 명세

이 문서는 교육용 발주 실습의 업무 조건과 완료 기준입니다. 현재 요청한 단계만 적용합니다.
공개 클래스·함수 이름, 매개변수와 파일 위치는 [project/AGENTS.md](project/AGENTS.md)에서 확인합니다.
조사·승인·변경·보고 절차는 [ai_build_rules.md](ai_build_rules.md), 결과 판정은
[ai_review_rules.md](ai_review_rules.md)를 따릅니다. 이미 있는 구현을 조사해 이어서 사용합니다.

## 실습 범위

- 요청 검증 → 업무 판단 → 저장 → API 연결 순서로 같은 `project/`에서 진행합니다.
- 요청 검증과 업무 판단은 DB 없이 실행합니다. 상품 조회는 API 연결, 쓰기는 저장 함수의 책임입니다.
- 발주 마스터·모든 상세·감사만 저장합니다. 상품 단가·활성 상태를 변경하지 않습니다.
- 재고·예치금·미수금·신용한도 검사나 변경, 새로운 모델·업무 규칙은 추가하지 않습니다.
- Core는 로컬 SQLite를 사용합니다. PostgreSQL·Supabase·동시성은 이번 실행 검증 범위가 아닙니다.
- 인증·회사 소유권·멱등성·마감과 기존 발주 수정 기능은 구현하지 않습니다.
- 현재 단계의 파일만 변경하고 시작 파일과 이전 단계의 구현·테스트는 보존합니다.

## 8.2 요청 검증

### 입력과 허용 값

원본 JSON은 다음 구조입니다. `master`는 발주 기본 정보, `details`는 품목 객체들의 배열입니다.

```json
{
  "master": {
    "dept_code": "10",
    "emp_code": "E001",
    "delivery_code": 101,
    "is_vat": "2"
  },
  "details": [{"prod_code": "A001", "qty": 5}]
}
```

| 값 | 조건 |
|---|---|
| `dept_code`, `emp_code` | 문자열의 앞뒤 공백을 제거한 뒤 1~20자 |
| `delivery_code` | 양의 정수. 문자열·bool·실수·null은 거부 |
| `is_vat` | 문자열 `"1"` 또는 `"2"`. 키가 없을 때만 `"1"`을 사용. null과 다른 값은 거부 |
| `details` | 한 건 이상의 배열. 각 항목은 객체 |
| `prod_code` | 문자열의 앞뒤 공백을 제거한 뒤 1~50자 |
| `qty` | 양의 정수. 문자열·bool·실수·null은 거부 |

공백을 제거한 상품코드가 같으면 중복입니다. 서버 소유 값인 회사·거래처·상태·단가·합계는
입력에 있어도 반환값으로 복사하지 않습니다. 허용한 발주 기본 정보와 품목 값은 유지합니다.
입력 원본은 변경하지 않고, 검증된 발주·품목 값은 불변으로 만들며 품목 목록은 `details`의 튜플로 보관합니다.
`Event`는 외부 메시지 이벤트가 아니라 다음 업무 단계로 전달할 불변 요청 값입니다.

### 오류 분류

| 오류 code | 조건 |
|---|---|
| `invalid_payload` | 요청 전체가 JSON 객체가 아님 |
| `invalid_master` | master 누락·객체가 아님·부서/사원/배송지/VAT 오류 |
| `invalid_detail` | details 누락·배열이 아님·빈 배열·품목이 객체가 아님·상품코드/수량 오류 |
| `duplicate_product` | 공백 제거 후 중복 상품코드 |

위 code는 후속 HTTP 변환에 사용하므로 임의의 공개 code로 바꾸지 않습니다.

### 완료 기준: DB 없는 테스트

- VAT `"1"`·`"2"`를 각각 명시한 정상 요청과 정상 발주·품목 값의 보존을 확인합니다.
- VAT 생략의 기본값 `"1"`, null·잘못된 문자열·숫자·bool 거부를 확인합니다.
- 수량 0·문자열·true 거부와 빈 상세를 검사합니다.
- 문자열 공백 제거와 공백 제거 후 중복 상품 거부를 검사합니다.
- 부서·사원 코드의 공백 제거 후 20자 통과·21자 거부, 상품코드 50자 통과·51자 거부를 검사합니다.
- 회사·거래처·상태·단가·합계가 결과에 없고 정상 정보는 유지되는지 검사합니다.
- 입력 원본 보존, 발주·품목 값의 대입 거부와 품목 목록의 튜플 저장을 확인합니다.
- 요청 전체·master·details의 오류 분류가 위 표와 맞는지 검사합니다.
- 대표 결과: 조작된 단가는 제외되고 상품코드 A001·수량 5는 유지됩니다.

## 8.3 업무 판단

### 입력과 계산

8.2의 검증된 요청 값과 서버 상품 스냅숏을 받습니다. 상품 스냅숏은 상품코드·서버 단가·활성 여부를
담는 불변 값이며 DB 모델 자체가 아닙니다. 상품코드로 스냅숏을 찾는 매핑을 사용합니다.

- 공급가액 = 서버 상품 단가 × 요청 수량.
- VAT `"2"`: 품목별 공급가액의 10%를 1원 단위로 반올림합니다. 0.5원은 올립니다.
- VAT `"1"`: VAT는 0원.
- 품목 합계 = 공급가액 + VAT. 전체 합계는 품목별 합계의 합입니다.
- 여러 품목을 요청 순서대로 확인하고 처음 발견한 오류를 발생시킵니다.
- 상품 없음·비활성은 `product_not_found`, 서버 단가 0 이하는 `invalid_unit_price`입니다.
- 회사는 서버가 전달한 `actor_corp_id`를 사용합니다. 생략했을 때만 기본값 `"branch01"`을 씁니다.
- 거래처는 `"admin"`, 신규 발주 상태는 `"10"`입니다. 클라이언트의 회사·거래처·상태·단가·합계는 쓰지 않습니다.

### 결과와 단계 연결

전체 계획은 회사·거래처·상태, 검증된 부서·사원·배송지·VAT, `total_amount`와 `details`를 담습니다.
각 품목 계획은 `prod_code`, `qty`, `unit_price`, `net_price`(공급가액), `vat`, `total_amount`를 담습니다.
계획·품목 값은 불변이며 `details`는 요청 순서의 튜플입니다. 금액은 원화 정수입니다.
계획은 저장할 값이며 실제 DB 저장 결과가 아닙니다.

요청 오류 네 가지와 `product_not_found`는 HTTP 400, `invalid_unit_price`는 HTTP 409로 매핑합니다.
이번 단계에서는 오류 매핑만 준비하고 실제 HTTP 연결은 만들지 않습니다.

### 완료 기준: DB 없는 테스트

- 서버 단가 1000·수량 5·VAT `"2"` → 공급가액 5000·VAT 500·합계 5500.
- 공급가액 1005·VAT `"2"` → VAT 101. VAT `"1"` → VAT 0.
- 여러 품목의 순서·품목별 계산·합산과 요청 순서의 첫 오류를 검사합니다.
- 상품 없음·비활성·단가 0·음수를 각각 검사합니다.
- 회사 기본값과 다른 서버 회사 전달, 거래처·상태, 클라이언트 값 무시를 검사합니다.
- 계획·품목 불변성, `details` 튜플과 오류별 HTTP 매핑을 검사합니다.
- 8.2 테스트도 계속 통과해야 합니다. DB 조회·저장이나 재고·금융 로직이 없어야 합니다.

## 8.4 저장

### 저장 조건

기존 업무 판단 함수의 반환 구조를 조사하고 그 저장 계획을 입력으로 사용합니다.
시작 모델을 사용하며 새 모델이나 별도 업무 규칙을 만들지 않습니다.

- 하나의 SQLAlchemy Session 트랜잭션에서 마스터 → 모든 상세 → 감사를 저장합니다.
- 키트의 연결 방식은 `with db.begin():` 안에서 마스터 flush → 상세 전체 flush → 감사 flush입니다.
- 마스터가 생성한 발주번호를 모든 상세와 감사에 연결하고 저장 함수는 그 번호를 반환합니다.
- 상세는 계획의 서버 단가·공급가액·VAT·합계를 그대로 저장합니다.
- 감사에는 `action="INSERT"`, 상세 건수와 총액을 기록합니다.
- 중간 커밋은 금지합니다. 정상 종료에서만 커밋하고 상세·감사 실패 시 전체를 롤백합니다.
- 상품 단가·활성 상태를 변경하지 않습니다.
- 저장 함수가 요구하는 세션·트랜잭션 상태를 실제 코드에서 조사해 docstring에 설명합니다.
- 8.5의 상품 조회·저장 연결은 이번 단계에서 미리 구현하거나 별도 방식으로 확정하지 않습니다.

### 완료 기준: 인메모리 SQLite 테스트

- 파일 DB·서버 없이 테스트마다 격리된 인메모리 SQLite를 사용합니다.
- 시작값은 상품 A001·단가 1000·활성과 마스터·상세·감사 0·0·0건입니다.
- 정상 단건 계획 저장 후 1·1·1건, 마스터 합계 5500, 상세 단가 1000·공급가액 5000·VAT 500·합계 5500을 검사합니다.
- 감사 INSERT·상세 건수 1·총액 5500과 상품 단가·활성 상태 보존을 검사합니다.
- 여러 품목 저장에서 모든 상세의 값·발주번호 연결과 감사 건수·총액이 계획과 일치하는지 검사합니다.
- 두 건 이상 중 뒤쪽 상세 INSERT와 감사 INSERT를 각각 SQLAlchemy 테스트 이벤트로 실패시킵니다.
- 실패 뒤 새 세션에서 세 저장 테이블이 0·0·0건인지 검사합니다. 제품 코드에 실패 스위치를 넣지 않습니다.
- 이벤트 리스너는 테스트가 실패해도 반드시 제거합니다.
- 뒤쪽 상세 실패 전에 앞선 INSERT가 실제 실행 완료됐는지 확인합니다. 확인하지 못했다면 그 INSERT까지
  롤백됐다고 단정하지 말고, 저장 시도 전체가 취소돼 기록이 남지 않았다는 확인 범위만 보고합니다.
- 저장 테스트와 8.2·8.3 테스트를 실행합니다. 인메모리 결과를 PostgreSQL·동시성·실제 HTTP의 근거로 쓰지 않습니다.

## 8.5 API 연결

### 요청 처리와 응답

교육용 `POST /franchise/order`에서 기존 요청 검증 → 서버 상품 조회 → 업무 판단 → 저장을 연결합니다.
계산·저장 로직은 재사용하고 FastAPI 앱에 라우터를 등록합니다.

- 요청 상품을 한 번 조회하고 ORM 객체가 아닌 상품 스냅숏을 업무 판단에 전달합니다.
- 조회를 `with db.begin():` 안에서 끝내고 스냅숏을 추출한 뒤 판단합니다.
- 조회 트랜잭션이 종료된 세션으로 기존 저장 함수를 한 번 호출합니다.
- 성공은 HTTP 200과 아래 응답입니다. 발주번호는 DB가 생성하므로 초기 DB가 아니면 달라질 수 있습니다.

```json
{"status":"success","purchase_order_no":1,"order_status":"10","detail_count":1,"total_amount":5500}
```

- 입력·중복·상품 없음은 HTTP 400.
- 잘못된 서버 단가와 DB 무결성 충돌은 HTTP 409.
- 예상하지 못한 저장 오류는 HTTP 500. SQL과 내부 예외 문자열을 응답에 노출하지 않습니다.
- 기존 발주 수정이 없는 Core에서 상품 없음을 404로 바꾸지 않습니다.

### 완료 기준: 자동 테스트

- 앱 등록과 정상 200의 응답 필드·값을 검사합니다.
- 수량 0·상품 없음 400, 서버 단가 0·무결성 충돌 409, 내부 저장 오류 500을 검사합니다.
- 500의 내부 메시지 비노출을 검사합니다.
- 기존 요청 검증·업무 판단·저장 테스트도 모두 실행합니다.
- 앱 등록·Mock·자동 테스트를 실제 네트워크 HTTP 실행과 구분합니다.

## Core 최종 완료와 선택 범위

| 실제 실행할 Core 사례 | 확인할 결과 |
|---|---|
| 정상 요청 | HTTP 200·합계 5500·DB 마스터/상세/감사 1·1·1 |
| 수량 0 | HTTP 400·새 기록 없음·DB 1·1·1 유지 |
| 상품 값 | 단가 1000·활성 상태 유지 |

정상 요청은 새로 준비한 DB에 한 번만 보냅니다. 재시도 전 저장 여부를 확인합니다.
저장 중 실패의 전체 롤백은 8.4 자동 테스트로 확인합니다. 단가 0의 409는 자동 테스트에 유지하며,
실제 단가 변경·복구와 HTTP 409 확인은 선택 실습입니다.

완료 도구는 코드·테스트·앱 등록·파일 DB를 확인하지만 실제 HTTP 요청을 보내지 않습니다.
통합 리뷰는 공통 검증 지침에 따라 최신 코드와 실제 실행 결과를 대조합니다.
필수 검사에서 Fail·Not Run·테스트 없음·누락이 남으면 완료로 처리하지 않습니다.
범위 밖 보장은 해당 없음으로 표시합니다. 참고 구현과 테스트 개수를 맞추는 것은 완료 기준이 아닙니다.
