# 실습 3 — 같은 발주를 다시 승인하면 어떻게 될까요?

실습 2의 역할 검사를 완료한 뒤 진행합니다.

## 업무 중 같은 발주가 두 번 승인됐습니다

> **업무 담당자:** 오전에 관리자가 승인한 발주를 오후에 다른 관리자가 다시 승인했습니다. 같은 발주의 승인 처리가 두 번 반영됐어요.
>
> **개발자:** 두 사람 모두 승인 권한이 있는 사용자군요. 먼저 같은 발주에 다시 요청했을 때 어떻게 처리되는지 확인하겠습니다.

첫 회의에서는 역할과 회사 범위를 정했지만, 이미 승인된 발주를 다시 처리할지는 논의하지 않았습니다.

## 수정 전에 같은 상황을 재현합니다

키트에는 A회사 관리자 계정이 하나 있습니다. 이 계정으로 두 번 요청해 다른 관리자가 같은
발주에 새 승인 요청을 보낸 상황을 재현합니다. 직원별 승인 이력이나 동시 요청은 확인하지 않습니다.

1. **본 실습**에서 **실습 데이터 초기화**를 누르고 **A회사 관리자로 접속**합니다.
2. **발주 메뉴 열기**와 **1001 상세 조회**를 누릅니다. 승인 대기, 처리 횟수 `0`인지 확인합니다.
3. **발주 승인**을 누릅니다. 응답 `200`, 승인 완료, 처리 횟수 `1`을 확인합니다.
4. 초기화하지 않고 **승인 요청 직접 보내기**를 누릅니다.
5. 상태 제한이 없는 구현이라면 다시 `200`이 반환되고 승인 완료 상태에서 처리 횟수가 `2`로 늘어납니다. 실제 결과를 확인합니다.

상태 표시만 보면 추가 처리를 놓칠 수 있습니다. 처리 횟수도 함께 확인합니다.
이미 재승인이 거부된다면 사건을 재현하려고 검사를 지우지 마세요. AI에게 코드를 수정하지 말고
거부 조건과 추가된 이유를 확인하게 합니다. 재현하지 않은 `200`·횟수 `2`를 자신의 결과로 기록하지 않습니다.

## 업무 회의에서 상태 규칙을 보완합니다

> **개발자:** 현재 역할 규칙만으로는 이미 승인한 발주를 다시 처리해도 되는지 정할 수 없습니다. 승인 완료된 발주에 새 승인 요청이 오면 어떻게 처리해야 하나요?
>
> **업무 담당자:** 승인 대기 발주만 승인할 수 있게 해 주세요. 이미 승인한 발주는 다시 처리하지 말고, 승인 완료된 건이라는 안내를 보여 주세요.
>
> **개발자:** 거부된 요청은 기존 발주 상태와 승인 처리 횟수를 바꾸지 않도록 하겠습니다.

확정한 상태 규칙을 기존 역할 검사에 추가합니다. 상태는 서버가 DB에서 읽은 값으로 판단하며,
상태 제한이 이미 있다면 확정한 기준에 필요한 보완만 합니다.

## AI에게 요청하기

```text
AGENTS.md와 README.md를 읽고 현재 역할 검사와 조회·저장 흐름을 조사하세요.
이미 승인된 발주에 다른 관리자가 새 승인 요청을 보내 같은 승인이 다시 처리되는 문제가 접수됐습니다.
상태 검사 유무와 변경할 파일·이유를 알린 뒤 회의에서 확정한 다음 규칙을 구현하세요.
이미 기준을 만족하는 검사가 있다면 유지하고 불필요한 변경은 하지 마세요.

- 요청값 대신 DB에서 읽은 현재 상태로 판단하세요. 승인 대기 발주만 승인할 수 있습니다.
- 그 밖의 상태에 새 승인 요청이 오면 409와 '승인 대기 발주만 승인할 수 있습니다.'로 거부하세요.
- 거부 후 상태·처리 횟수를 유지하세요. 관리자 정상 승인, 조회 담당자 403과 회사 차단도 유지하세요.

수정 범위는 AGENTS.md의 실습 3입니다. 기존 저장 처리를 사용하세요.
요청 키·재전송 처리·재고 변경은 추가하지 않습니다. 변경 파일·실행 결과·미확인 항목을 보고하세요.
```

## 수정 후 같은 상황을 다시 확인합니다

AI 작업 후 브라우저를 새로고침하고 **본 실습**의 **실습 데이터 초기화**를 누릅니다.
수정 전 재현으로 바뀐 데이터를 되돌리는 것이며 수정한 코드는 유지됩니다.
초기화하면 접속도 해제되므로 **A회사 관리자로 접속**합니다. 이후 두 요청 사이에는 초기화하지 않습니다.

1. A회사 관리자로 발주 메뉴를 열고 1001번 상세를 선택합니다.
2. 발주 승인을 한 번 누르고 응답 200을 확인합니다.
3. 승인 완료 상태와 승인 처리 횟수 1을 확인합니다.
4. 승인 요청 직접 보내기를 눌러 같은 발주에 새 요청을 보냅니다.
5. 응답 409와 위 거부 메시지를 확인합니다.
6. 상태가 승인 완료, 처리 횟수가 1로 유지되는지 확인합니다.

직접 요청 장치는 버튼 표시와 별개로 매번 새 요청을 보냅니다. 이전 요청 키를 재사용하지 않습니다.
Ch.3에서는 같은 요청의 재전송을 다뤘습니다. 이번에는 새 요청이라도 끝난 업무를 다시 실행할 수 있는지 확인합니다.
이번 예제에서는 상태와 처리 횟수로 추가 처리가 없었는지 확인합니다.

### 선택 확인: 처음부터 승인 완료인 발주

4.3을 마친 뒤 더 확인하고 싶다면 A회사 관리자로 **1002 상세 조회**를 엽니다.
시작부터 승인 완료·처리 횟수 1인 발주입니다. **승인 요청 직접 보내기**를 눌러
`409`와 '승인 대기 발주만 승인할 수 있습니다.', 승인 완료·횟수 1 유지를 확인합니다.
이 사례는 방금 승인한 1001번뿐 아니라 기존 승인 완료 데이터에도 같은 규칙이 적용되는지 확인합니다.

## 실제 처리 흐름 따라가기

```text
AGENTS.md와 최신 코드를 읽고 상태 검사를 안내해 주세요.
발주 조회 → 역할 검사 → 현재 상태 검사 → 상태·횟수 저장 → 응답 순서로 정리하세요.
상태를 DB에서 읽는 곳과 재승인을 저장 전에 거부하는 곳을 표시하세요.
각 단계의 파일·함수·검색어를 한 줄로 적고, 찾지 못한 곳은 미확인으로 표시하세요.
코드 조사만 하고 파일 수정이나 명령 실행은 하지 마세요.
```

AI의 안내를 따라 현재 상태가 DB에서 나온 값인지, 거부가 저장 전에 일어나는지 확인합니다.
전체 SQL을 외우거나 추적 보고서를 다시 쓸 필요는 없습니다.

## AI 검증과 완료

수정 후에는 첫 승인만 `200`으로 성공하고, 새 재승인 요청은 `409`로 거부되어야 합니다.
두 번째 요청 뒤에도 승인 완료·처리 횟수 `1`이면 추가 승인이 반영되지 않은 것입니다.
앞에서 본 결과와 비교하고 아래 프롬프트를 그대로 실행합니다.

```text
AGENTS.md를 읽고, 상태 규칙을 추가한 본 실습에서
다음 동작이 지켜지는지 직접 확인해 주세요.

1. A회사 관리자가 자기 회사의 승인 대기 발주를 승인하면
   승인 완료로 바뀌고, 승인 처리 횟수는 1이어야 합니다.
2. 같은 발주에 새 승인 요청을 보내면 거부되고,
   승인 완료 상태와 처리 횟수 1이 유지되어야 합니다.
3. 조회 담당자는 자기 회사 발주를 볼 수 있지만 승인할 수 없어야 합니다.
4. A회사 관리자도 B회사 발주를 승인할 수 없어야 합니다.

코드는 수정하지 마세요.
확인한 결과와 확인하지 못한 항목을 짧게 알려 주세요.
이미 승인한 발주를 다시 처리하지 못하게 막는 코드 한 곳도 짚어 주세요.
```

AI가 짚어 준 상태 검사 코드를 엽니다. DB에서 읽은 상태가 승인 완료이면 저장 전에
거부하는지 확인합니다. 이번 검사는 같은 요청의 재전송이 아니라 같은 발주에 보낸 새 요청을 대상으로 합니다.

- [ ] 첫 승인 200 뒤 새 승인 요청은 409로 거부되고, 승인 완료·횟수 `1`이 유지됐습니다.
- [ ] AI가 안내한 코드에서 DB의 현재 상태를 검사하고 저장 전에 재승인을 거부하는지 확인했습니다.

**이번에 배운 것:** 권한이 있는 사용자라도 현재 업무 상태에 따라 요청을 거부해야 합니다.
