# 기초 실습 작업 규칙

## 범위

- 현재 VS Code에서 연 Chapter 폴더 안의 파일만 수정한다.
- 다른 `chXX` 폴더와 `reference-app`은 읽거나 수정하지 않는다.
- 요청받지 않은 완성 코드를 미리 생성하지 않는다.

## 작업 순서

1. 현재 Chapter의 `AGENTS.md`와 `README.md`를 읽는다.
2. 요구사항, 기존 파일, 변경 범위와 검증 방법을 먼저 보고한다.
3. 독자의 승인을 받은 뒤 최소 변경만 적용한다.
4. 변경 파일과 실행한 검증을 `Pass`, `Fail`, `Not Run`으로 구분한다.

## 공통 보고 규칙

- 변경 파일, 실제 실행 명령과 결과, 원고가 요구한 사례의 판정을 간결하게 보고한다.
- 검사는 `Pass`(실행하여 통과), `Fail`(실행하여 실패), `Not Run`(검사가 있으나 미실행),
  `테스트 없음`(요구한 검사가 없음)으로 구분한다. 원고의 실습 범위 밖 항목은
  `실습 대상 아님`, 요구하지 않은 항목은 `요구사항 아님`으로 표시한다.
- 근거 표는 `확인 항목 | 파일 경로:행:열 | 실제 함수·테스트 이름 | 확인할 내용`으로 작성한다.
- 경로는 현재 Chapter 폴더(`chXX/`)부터 표시하고 행과 열은 1부터 센다.
  보고 전에 최신 파일을 다시 읽어 이름과 위치가 일치하는지 확인한다.
- 원고가 지정한 대표 사례 테스트는 입력과 단언문 위치를 각각 표시한다.
  추가 검사는 요약하고, 테스트 개수는 실제 실행 결과로 확인한다.
  일부 테스트 이름만 나열한 것으로 전체 개수를 추정하지 않는다.
- 검증 단계에서는 이번 변경 파일과 diff 또는 비교할 기준본을 확인한다.
  둘 다 없으면 이전 파일 대비 변경 범위를 확인하지 못했다고 보고한다.
  최신 파일의 업무 규칙 검증과 이전 파일 대비 변경 범위 검증을 구분하며,
  수정 시각을 diff의 대체 근거로 사용하지 않는다.
- 원고가 지정한 최소 근거를 독자가 직접 확인할 수 있도록 안내한다.
  실행하지 않았거나 실습 범위 밖인 작업을 검증했다고 보고하지 않는다.

## 안전 규칙

- `.env`, 비밀번호, API key, JWT와 실제 DB URL을 읽거나 출력하지 않는다.
- 운영·공용 DB에 SQL을 실행하지 않는다.
- `DROP`, `DELETE`, 폴더 삭제와 이름 변경은 현재 Chapter가 명시한 격리 대상에서만 수행한다.
- 테스트를 실행하지 않았다면 통과로 추정하지 않는다.
