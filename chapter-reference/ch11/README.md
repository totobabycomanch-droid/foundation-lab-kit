# Chapter 11 주문 승인 참조 구현

이 자료는 개편된 ch11의 업무 결과와 생성 코드를 비교하는 완성 예제입니다.
독자는 `practice-workspace/ch11/`의 시작 기반에서 AI에게 구현을 요청합니다.
AI가 이 참조 코드를 통째로 복사해 실습을 대신 완성하지 않습니다.
개인 작업이 있다면 먼저 보존하고 차이와 필요한 부분만 비교합니다.

## 파일과 역할

| 파일 | 역할 | 비교 위치 |
|---|---|---|
| `approve_order.sql` | 새 테이블 세 개·수량 저장·재고 검사·재승인 방지·함께 저장 | 백엔드 `sql/`의 AI 생성 스키마 |
| `main.py` | 수량 저장·승인·두 주문 조회·오류 구분·커밋 뒤 응답 | 백엔드 `api/main.py` |
| `ApproveOrder.vue` | 수량 입력·별도 저장·승인·DB 재조회·오류와 미확인 결과 구분 | 화면 `src/components/ApproveOrder.vue` |
| `App.vue` | 주문 승인 화면 등록 | 화면 `src/App.vue` |

백엔드는 `practice-workspace/ch11/workspace/erp-project/`, 화면은 `workspace/frontend-project/`입니다.
참조 폴더에서 직접 서버를 실행하지 않습니다. API는 실행 기반의 `lab_db.py`를 사용합니다.
완성 예제를 시험하는 별도 폴더에서도 실행 도구와 기존 의존성·잠금 파일을 함께 준비합니다.

## DB 적용과 두 사례

- SQL은 새 전용 실습 DB를 대상으로 검토한 뒤 백엔드 `sql/`에 보존하고 `lab.py apply 파일명.sql`로 적용합니다.
- 기존 테이블을 삭제하거나 새 구조로 자동 이전하지 않습니다. 이미 적용한 SQL과 참조 SQL을 중복 실행하지 않습니다.
- 생성 SQL은 테이블·함수만 정의합니다. 독자용 데이터는 `lab.py prepare`가 준비하고 기존 결과는 보존합니다.
- A·B는 수량 1에서 시작합니다. 독자가 각 주문의 수량을 3으로 바꿔 별도로 저장하고, 새로고침해 저장된 수량을 확인합니다.
- 정상 A는 재고 10에서 수량 3으로 승인해 `PAID`·재고 7·원장 1건, `-3`이 됩니다.
- 부족 B는 다른 상품의 재고 2에서 수량 3을 저장한 뒤 승인 요청합니다. 거절 뒤에도 수량 3·`CREATED`·재고 2·원장 0건입니다.
- A와 B 사이에는 초기화하지 않습니다. 재실습이 필요할 때만 AI가 지정 사례를 재준비합니다.
- 실제 저장 결과는 [두 주문 조회 SQL](../../practice-workspace/ch11/workspace/erp-project/sql/view_orders.sql) 하나로 대조합니다.
- 원장 없는 주문은 `ledger_count=0`, `qty_change=NULL`입니다. 정상 A는 `ledger_count=1`, `qty_change=-3`입니다.

## 저장과 화면 처리

수량 저장은 `POST /orders/quantity`에서 `change_order_quantity`를 호출합니다. 주문 행을 잠그고 `CREATED` 상태인지 확인한 뒤 수량만 바꾸며 재고·원장·상태는 바꾸지 않습니다.
수량은 양의 정수만 허용하지만 현재고보다 큰 값도 저장합니다. 재고 검사는 승인할 때 수행합니다.
화면은 미저장 입력이 있으면 승인을 막고 수량 저장 뒤 DB를 재조회합니다. 승인 완료 후에는 입력란·수량 저장·승인을 잠급니다.

주문 행을 잠근 뒤 최신 상태를 검사하고, 이미 승인된 주문은 쓰기 전에 거절합니다.
상품의 재고 행도 잠근 뒤 수량을 검사합니다. 재고 차감·주문별 원장·승인 상태는 같은 트랜잭션에서 저장합니다.
이 실습에서는 한 주문을 한 번 전량 승인하므로 원장의 주문 참조에도 UNIQUE 조건을 둡니다.
부분 승인·승인 취소·반품의 원장 모델은 이 예제의 범위가 아닙니다.

API는 `commit()` 성공 뒤에만 승인 성공을 응답합니다. 알려진 업무 거절은 고정된 사유의 400으로 변환하고 내부 예외 전문을 응답하지 않습니다.
커밋 중 연결 장애는 결과 미확인으로 안내합니다. rollback 호출이 저장 취소를 보장한다고 설명하지 않습니다.
화면은 `GET /orders`의 상태·현재고를 표시하고 승인 뒤 다시 조회합니다. 재고를 화면에서 임의 차감하지 않습니다.
저장 성공 뒤 조회 실패와 승인 응답 유실을 구분하며, 상태를 확인하기 전 무조건 재승인하지 않습니다.

## 검증 범위

참조 구현 제공은 실제 DB 적용이나 화면 검증의 실행 증거가 아닙니다.
검사할 때는 실제 PostgreSQL 결과, HTTP 검사, 테스트 응답을 사용하는 화면 검사와 빌드를 구분합니다.
자동 DB 검사는 독자용 A·B와 별도 주문·상품을 사용해야 합니다. 직접 관찰값은 독자가 작성합니다.
인증·회사별 접근 제한·외부 공개 배포는 포함하지 않습니다. `corp_id`는 회사 소속 기록이며 접근 제어가 아닙니다.
구현 뒤 제공된 `verify_core.py`로 DB·HTTP·빌드를 검사하고, 독자가 화면에서 A 정상 승인과 B 재고 부족을 직접 확인합니다.
