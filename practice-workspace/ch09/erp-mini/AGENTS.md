# Chapter 9 erp-mini 규칙

이 지침은 원고의 짧은 생성·검증 요청과 함께 적용한다. 상위 공통·Chapter 지침의 작업 순서와
보고 규칙을 따른다. 생성 요청에서는 아래 범위만 구현하고, 검증 요청에서는 파일을 수정하지 않는다.
기존 지침·구현과 요청이 충돌하면 차이와 최소 변경안을 보고한 뒤 확인을 기다린다.

## 작업 범위와 실행

- 이 파일 아래의 경로는 `erp-mini/` 기준이다. 상태 규칙은 `domain/order.py`, 실제 실행은
  `main.py`, 자동 검사는 `tests/test_erp_flow.py` 세 파일에 둔다.
- Python 표준 라이브러리만 사용하고 테스트는 `unittest`로 작성한다.
- 주문 규칙에는 DB·HTTP·결제·재고를 연결하지 않는다. 제공 관찰 서버만 HTTP로 공개 행동을 연결한다. 9.5는 읽기 구간이며 확장 코드는 추가하지 않는다.
- 지침·패키지 파일·`requirements.txt`, 상위 `run.ps1`·`checks/`·`reference/`는 수정하지 않는다.
  정상 생성·검증 중 `reference/`는 답안으로 읽거나 복사하지 않는다.
- 상위의 web_server.py, frontend/, verify_observation.py, observation-baseline.json과 checks/test_web.py는 제공 관찰 도구다. 업무 구현 요청에서 수정하지 않는다.
- 범위 밖 파일이 필요하면 적용 전에 파일과 이유를 보고한다.
- 실행 명령은 `ch09/`에서 `./run.ps1 demo`, `./run.ps1 test`, `./run.ps1 verify`를 사용한다.
  실제 작업 위치를 조사하고, AI의 기준 위치가 독자 터미널과 같다고 가정하지 않는다.

## 주문의 업무 규칙

- 신규 상태는 `PENDING`이다. 정상 경로는 `PENDING → APPROVED → SHIPPING → DELIVERED → COMPLETED`이다.
- 취소는 `PENDING → CANCELLED`만 허용한다. `COMPLETED`·`CANCELLED`에서는 모든 행동을 거부한다.
- 허용되지 않은 행동은 `ValueError`로 거부하고 요청 전 상태를 유지한다.
- 외부에서 공개 `status`를 직접 대입하면 `AttributeError`로 거부하고 기존 상태를 유지한다.

## 실행 예제와 연결할 공개 사용 규약

- `Order(order_id=1)`과 읽기 전용 `status`, `approve()`, `ship()`, `confirm_delivery()`,
  `complete()`, `cancel()`을 제공한다. 메서드는 각각 승인·출고·배송 확인·완료·취소를 뜻한다.
- `status`는 여섯 상태 이름 중 하나인 일반 `str` 객체를 반환한다. `print(order.status)`는
  상태 이름과 줄바꿈만 출력한다. 내부에서 Enum을 써도 외부에서 `.value` 변환이 필요 없고
  `OrderStatus.PENDING` 같은 표시는 나오지 않아야 한다.
- 내부용 속성의 밑줄은 관례이며 외부 접근을 완전히 차단하지 않는다고 설명한다.
  내부 속성 접근 차단은 요구사항이 아니다.
- 상태 규칙은 전이 표 한 곳에 모으고, 모든 행동 메서드가 공통 검사에 통과한 뒤 상태를 바꾼다.
- 각 메서드와 테스트에 입력·결과를 설명하는 짧은 docstring을 작성한다.

## 실제 실행과 테스트 기준

- `main.py`는 정상 승인·출고·배송 확인·완료의 각 단계, 배송 완료 후 재승인, 승인 대기에서
  배송 확인, 공개 상태 직접 대입, 승인 후 재승인을 실제 호출·대입으로 실행한다.
  예상 문구만 출력하지 않는다. 예상 예외를 처리한 뒤 실제 상태를 표시하고 다음 사례를 계속한다.
- 생성 테스트는 위 사례와 새 주문의 출고 거부, 취소·완료의 허용 경로,
  두 종료 상태에서 모든 행동의 거부를 검사한다.
- 자동 실행·테스트는 사례마다 새 주문을 만들고 한 사례의 행동은 같은 주문에 이어서 실행한다.
  상태 준비에는 공개 행동만 사용하며 내부 상태를 덮어쓰지 않는다.
  독자의 대화형 직접 처리는 같은 주문을 끝까지 사용하는 별도 관찰이다.
- 기대값은 업무 규칙에서 작성하며 구현의 전이 표를 읽어 자동 생성하지 않는다.
  정상 사례는 각 행동 뒤 상태, 거부 사례는 지정된 예외와 요청 전 상태 보존을 단언한다.
- 여섯 상태에서 `type(order.status) is str`와 캡처한 `print(order.status)` 출력을 각각 검사한다.
  값의 동등성이나 `isinstance(status, str)`만으로 두 조건을 확인했다고 판정하지 않는다.
- 생성 테스트 기대값이 업무 규칙과 다르면 차이와 올바른 기준을 보고한다. 생성·수정 요청에서는
  업무 규칙에 맞게 바로잡되, 통과 목적으로 올바른 기대값을 느슨하게 바꾸지 않는다.
  검증 요청에서는 문제와 최소 수정 범위만 보고한다. 업무 규칙·고정 검사는 유지한다.

## 검증과 완료 보고

- 최신 세 구현 파일·고정 검사와 이번 변경 내역을 확인한다. 비교할 기준본이 없다면
  이전 파일 대비 변경 범위를 확인하지 못했다고 보고한다.
- 예제·생성 테스트·고정 검사와 ./run.ps1 verify-web을 실제 실행하고, 이전 답변을 실행 결과로 대신하지 않는다.
  상위 공통 보고 규칙에 따라 변경 파일, 실행 명령·결과와 업무 규칙별 판정·근거 위치를 보고한다.
- 독자의 관찰을 정답으로 가정하지 않는다. 관찰·AI 재실행·코드·테스트 근거를 구분하고
  차이의 원인을 조사한다. 자동 검사로 독자의 직접 실행을 대신했다고 보고하지 않는다.
- `main.py`의 실제 호출과 예외 처리, 전이 표·공통 검사·직접 대입 거부 근거를 읽고 보고한다.
  테스트가 기대값을 독립적으로 작성하고 예외·상태 보존을 모두 단언하는지도 확인한다.
- 반환 형식·출력 검사 등 필요한 테스트가 없으면 누락으로 보고한다. 고정 검사 통과를
  예제·생성 테스트 내용 검토까지 완료했다는 뜻으로 확대하지 않는다.
- 독자가 직접 읽을 대표 근거는 배송 완료 후 재승인 테스트이다. 최신 파일에서 상태를 준비하는
  코드, 예외 검사, 거부 후 `DELIVERED` 유지 단언문의 위치를 지정한다.
- 내부 속성 접근 차단은 `요구사항 아님`, DB 저장·동시 요청·멱등성은 `실습 대상 아님`으로 표시한다.
  HTTP 검사는 제공 관찰 서버와 객체 연결만 확인하며 실제 ERP API 검증으로 표현하지 않는다.
  이 예제로 검증하지 않은 보장을 완료했다고 보고하지 않는다.
