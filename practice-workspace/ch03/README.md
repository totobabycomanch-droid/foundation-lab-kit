# Chapter 3 — 작은 발주 등록 화면

AI가 정상 저장, 중복 클릭 방지, 서버 재전송 처리, 회사별 조회 제한을 차례로 구현하는 실습이다.
초기 화면에는 관찰 장치만 있고 저장 기능은 아직 구현되지 않았다.

## 실행

Python 3.12 이상과 Node.js 22 이상을 준비한다. 첫 설치에는 인터넷 연결이 필요하다.
VS Code에서 이 `ch03` 폴더를 열고 PowerShell에서 실행한다.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\start_lab.ps1
```

`http://127.0.0.1:8303`을 연다. 스크립트는 이 폴더의 `.venv`와 `node_modules`에 의존성을
설치한다. 서버 종료는 해당 터미널에서 Ctrl+C다. AI가 수정하면 서버가 다시 읽는다.
화면은 새로고침한다. 다른 프로그램이 포트를 사용하면 `-Port 8304`로 실행하고 같은 포트로 접속한다.

## 제공되는 것

| 위치 | 역할 |
|---|---|
| `backend/order_write.py` | AI가 구현할 발주 저장 API |
| `frontend/order-form.js` | AI가 구현할 Vue 입력 폼과 저장 동작 |
| `backend/order_replay.py` | 세 번째 실습에서 AI가 구현할 동일 요청 저장 판단 |
| `backend/company_read.py` | 네 번째 실습에서 AI가 구현할 회사별 상세 조회 |
| `_starter/` | 위 네 파일의 변경 전 기준본. 수정 금지 |
| `backend/store.py` | 로컬 SQLite 저장과 관찰 수치 |
| `backend/app.py` | 서버·관찰 API·저장 요청의 1.2초 대기 |
| `frontend/app.js` | 서버에서 요청 횟수와 저장 목록을 읽는 관찰 화면 |
| `frontend/order-transport.js` | 요청 키·본문 보관과 동일 요청 재전송. 수정 금지 |
| `backend/lab_auth.py` | 조회용 테스트 사용자와 서버 세션. 수정 금지 |
| `frontend/company-probe.js` | 사용자 선택·회사 표시·실제 조회 응답 표시. 수정 금지 |

SQLite는 Python에 포함된 파일 DB다. 실습 데이터만 `.lab/orders.sqlite3`에 저장한다.
실제 Supabase, ERP 계정과 Docker는 사용하지 않는다. 로컬 상세 조회의 회사 제한을 확인하며,
실제 ERP 전체의 데이터 격리나 운영 DB의 동시성을 검증하는 환경은 아니다.

## 관찰 기준

- 요청 횟수는 서버가 받은 POST `/api/orders` 횟수다. 실패한 저장 요청도 포함한다.
- 저장 목록은 GET `/api/orders`로 실제 SQLite 데이터를 다시 조회한 결과다.
- 화면은 약 0.4초마다 관찰 결과를 갱신한다. 성공 응답 직후 잠시 기다린다.
- 각 실험 전에 `실습 데이터 초기화`를 누른다. 저장 요청 처리 중에는 초기화할 수 없다.
- 초기화는 이 실습의 저장 데이터와 요청 수치만 지운다. 코드와 의존성은 보존한다.
- 서버를 다시 실행해도 저장 데이터는 남는다. 요청 횟수는 서버 시작 후부터 센다.
- 첫 실습은 정상 저장 한 번, 두 번째 실습은 저장 중 연속 클릭을 확인한다.
- 세 번째 실습은 정상 저장 후 오른쪽의 `같은 요청 다시 보내기`를 한 번 누른다.
  요청 횟수 2, 저장 건수 1을 확인하고, 처음 응답과 재전송 응답의 발주 ID도 따로 비교한다.
- 재전송 버튼은 왼쪽 저장 함수의 중복 클릭 방지를 거치지 않는다. 입력 폼의 현재 값과 무관하게
  전송기에 보관한 마지막 요청 본문과 같은 키를 보낸다. 새 일반 저장은 새 키를 만든다.
- 초기화하면 서버의 발주·키 기록과 브라우저의 요청·응답 기록을 함께 비운다.
  새로고침하면 브라우저의 기록만 없어지며 DB의 발주·키 기록은 남는다.
- 서버 재전송 처리는 `order_replay.py`에 시작용 빈 함수만 제공한다. 첫 두 실습은 호출하지 않는다.
- 같은 키로 다른 품명·수량을 보내면 서버가 409로 거부해야 한다. 키 누락·형식 오류는 400이다.

## 회사별 조회

- 화면 아래 `회사별 조회 실습`에서 `A회사 사용자로 접속`을 누른다.
- 서버의 고정 사용자 매핑으로 user_a/A회사 또는 user_b/B회사 세션을 만든다.
  쿠키에는 서버가 발급한 무작위 세션 식별자를 넣는다. 회사 정보는 서버에서 찾는다.
- 사용자 선택은 로컬 실습 편의를 위한 기능이다. 운영용 인증·사용자 등록으로 사용하지 않는다.
- A회사 사용자로 A회사 발주 조회는 200, B회사 발주 조회는 404여야 한다.
- B회사로 바꾸면 B회사 발주가 200으로 조회되어야 한다. 사용자 전환 시 이전 결과 표시는 비운다.
- 조회용 `company_orders`에는 A/1001/`A회사 테스트 발주`/2와 B/2001/`B회사 테스트 발주`/3이 있다.
- 이 두 건은 저장·재전송용 목록과 별도 데이터다. 저장 건수·저장 요청 횟수에는 포함되지 않는다.
- 초기화 버튼은 저장·재전송 데이터만 비운다. 조회용 고정 데이터와 테스트 세션은 유지한다.
- 서버 재시작 후에는 세션이 사라지므로 테스트 사용자를 다시 선택한다.
- 상세 조회 API는 처음에는 501이다. 회사별 조회 실습에서 AI가 구현한다.

## 오류가 나면

- Python 또는 npm을 찾지 못하면 해당 도구 설치 후 VS Code 터미널을 새로 연다.
- 관찰 화면에 연결 오류가 나오면 서버 터미널의 오류를 확인한다.
- API의 501은 저장 기능이 미구현이라는 뜻이다. 설치 오류가 아니다.
- 작업 코드를 처음부터 다시 작성하려면 `_starter/`를 읽어 네 작업 파일과 비교한다.
  자동 덮어쓰기나 다른 Chapter의 초기화 도구는 사용하지 않는다.
