# Chapter 4 작업 규칙

이 지침은 독자 실습의 작업 경계다. 키트 제작자의 승인된 개편 작업과 구분한다.
먼저 이 파일과 README.md를 읽고 현재 실습의 요구사항과 허용 범위를 확인한다.
업무 정책은 현재 원고·lesson의 확정된 회의 내용을 근거로 한다.

## 단계별 수정 범위

- 실습 1: 업무 회의와 역할·회사 규칙을 읽는다. 작업 지침, README.md, lessons/01_requirement.md만 읽으며 코드는 수정하지 않는다.
- 실습 2 승인 권한: backend/approval_rules.py와 frontend/approval-action.js만 수정한다. 서버가 확인한 역할로 승인 권한을 판단하고, 조회 담당자의 일반 승인 버튼을 제한해 이유를 표시한다. 확인 화면(frontend/app.js)과 다른 서버 코드는 유지한다. 상태 제한은 실습 3에서 추가한다.
- 실습 3: backend/approval_rules.py의 현재 상태 검사만 추가한다. 제공된 화면과 기존 역할·회사 검사를 유지한다.
- 실습 3은 수정 전 재현 → 상태 규칙 확정 → 최소 수정 → 수정 후 검증 순서다. 재현 중에는 코드를 수정하지 않는다. 이미 재승인이 거부된다면 검사를 지우지 않고 이유를 확인한다.
- 사건 속 다른 직원의 요청은 기존 A회사 관리자 계정으로 두 번 요청해 재현한다. 직원별 이력·동시 요청을 검증한 것으로 보고하지 않는다.
- 실습 1~3에서 결함 전용 모듈이나 다른 Chapter의 완성 코드를 읽어 후속 답을 가져오지 않는다.
- 실습 4 원인 조사: 요청·서버 사용자·대상 조회·판단·저장 흐름을 읽기 전용으로 추적한다.
- 실습 4 최소 수정: backend/defect_scope.py만 수정한다. 서버 세션의 사용자 회사로 승인 대상 조회를 제한한다. 결함 실습의 고정 역할·상태·저장 흐름과 본 실습은 유지한다.
- 각 생성·수정 프롬프트는 명시된 범위의 구현 승인이다. 변경 파일과 이유를 짧게 보고한 뒤 구현한다. 범위 밖 변경이 필요하면 적용 전에 이유를 보고한다.

## 제공 화면과 실행 근거

- frontend/app.js는 키트가 제공하는 확인 화면이다. 독자 AI는 수정하지 않으며 제공 파일 무결성 검사의 보호 대상이다.
- frontend/transport.js의 send는 실제 HTTP 상태 코드와 JSON 본문을 반환한다. 사용자·회사·역할은 서버 응답에서, 발주 상태·횟수는 서버 재조회에서 얻는다.
- 일반 승인 버튼은 실습 2에서 frontend/approval-action.js로 조회 담당자에게 제한한다. 직접 요청 버튼은 화면 제한과 별개로 서버의 거부를 확인하게 하므로 제한하지 않는다.
- 초기화는 선택한 실습의 데이터·세션을 초기 상태로 되돌린다. 코드는 보존하며 접속 사용자는 다시 선택한다.
- 승인 버튼 구현 때 새 라이브러리·API·사용자·요청 키·재전송 처리를 추가하지 않는다.
- 독자는 관찰 기록·보고문·캡처를 필수로 작성하지 않는다. 프롬프트는 빈칸 없이 실행하며, 실제 결과와 미확인 항목을 구분한다.

## 제공 파일 보호와 검증

- 서버 연결·저장소·사용자 세션·전송 함수·초기화·실행 환경은 제공 기능이다. backend/app.py, backend/store.py, backend/lab_auth.py, frontend/app.js, frontend/transport.js, frontend/index.html, frontend/style.css를 독자 실습에서 수정하지 않는다.
- _starter/는 누적 비교·복구의 시작 기준본이다. 독자 AI는 수정하지 않는다. 검증 시 최신 변경 파일을 해당 기준본과 비교한다.
- 실습 2 이후 검증에서 python verify_observation.py로 제공 파일을 검사한다. 이 통과는 업무 규칙이나 화면 동작의 통과를 대신하지 않는다.
- 실제 실행 명령·요청·응답·DB 재조회 근거를 보고한다. 코드 확인과 직접 실행을 구분하고, 독자의 앞선 조작을 직접 관찰한 것으로 보고하지 않는다.
- Pass는 실제 실행해 기준 충족, Fail은 실제 실행해 기준 미충족, Not Run은 미실행이다. 검사가 없으면 테스트 없음으로 구분한다. 실습 대상 밖 항목은 실습 대상 아님으로 표시한다.
- 코드 근거는 실제 최신 파일·함수·행 위치로 안내한다. 마지막에는 독자가 볼 핵심 코드 한 곳을 쉽게 설명한다.
- 실습 4 완료 후 선택 검증은 .venv/Scripts/python.exe verify_business_rules.py로 실행한다. 임시 사본에서 API 24개를 검사하며 시작본·중간 단계에는 완성 기준 통과를 요구하지 않는다.
- verify_observation.py, verify_business_rules.py와 기준 파일은 제공 검사다. 독자 AI는 변경하거나 기대값을 낮춰 실패를 감추지 않는다. 화면 검증은 실제 브라우저에서 별도로 수행한다.
- 실제 사용자·비밀정보·운영 DB를 사용하지 않는다. inputs/는 이전 비교 자료이며 실행형 실습의 정책 근거로 쓰지 않는다. 다른 Chapter와 reference-app은 읽거나 수정하지 않는다.
