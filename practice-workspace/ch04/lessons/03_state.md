# 실습 3 — 상태: 같은 발주를 다시 승인하면 어떻게 될까요?

## 업무 중 같은 발주가 두 번 승인됐습니다

역할 규칙을 구현한 뒤, 업무 담당자에게 연락이 왔습니다.

> **업무 담당자:** 오전에 관리자가 승인한 발주를 오후에 다른 관리자가 다시 승인했습니다. 같은 발주의 승인 처리가 두 번 반영됐어요.
>
> **개발자:** 두 사람 모두 승인 권한이 있는 사용자군요. 먼저 같은 발주에 다시 요청했을 때 어떻게 처리되는지 확인하겠습니다.

첫 회의에서는 승인할 역할과 회사 범위를 정했습니다. 이미 승인된 발주를 다시 처리할지는
논의하지 않았습니다. 두 번째 관리자가 권한을 가진 사용자여도, 끝난 승인을 다시 실행해도
되는지는 별도의 업무 결정입니다.

## 수정 전에 같은 상황을 재현합니다

키트에 준비된 A회사 관리자 계정으로 두 번 요청합니다. 다른 관리자가 같은 발주에
새 승인 요청을 보낸 상황을 이렇게 재현하고, 두 요청의 응답과 DB 처리 횟수를 비교합니다.

1. **본 실습**에서 **실습 데이터 초기화**를 누르고 **A회사 관리자로 접속**합니다.
2. **발주 메뉴 열기**와 **1001 상세 조회**를 누릅니다. 승인 대기, 처리 횟수 `0`인지 확인합니다.
3. **발주 승인**을 누릅니다. 응답 `200`, 승인 완료, 처리 횟수 `1`을 확인합니다.
4. 첫 승인 직후 같은 발주에서 **승인 요청 직접 보내기**를 누릅니다.
5. 상태 제한이 없는 구현이라면 다시 `200`이 반환되고, 승인 완료 상태에서 처리 횟수가 `2`로 늘어납니다. 자신의 화면에서 실제 결과를 확인합니다.

상태 표시만 보면 두 요청 모두 승인 완료여서 차이를 놓치기 쉽습니다.
처리 횟수를 함께 보면 같은 승인이 한 번 더 반영됐는지 알 수 있습니다.

> **5번에서 이미 `409`가 나왔다면** 오류가 아닙니다. 4.2에서 AI가 상태 검사까지 미리 넣은 것입니다.
> 검사를 지우지 말고, AI에게 "코드는 수정하지 말고 이 거부 조건이 어디에 있고 왜 들어갔는지
> 설명해 주세요"라고 요청합니다. 그다음 자신의 응답과 처리 횟수를 아래 회의의 기준과 비교합니다.

## 업무 회의에서 상태 규칙을 보완합니다

> **개발자:** 현재 역할 규칙만으로는 이미 승인한 발주를 다시 처리해도 되는지 정할 수 없습니다. 승인 완료된 발주에 새 승인 요청이 오면 어떻게 처리해야 하나요?
>
> **업무 담당자:** 승인 대기 발주만 승인할 수 있게 해 주세요. 이미 승인한 발주는 다시 처리하지 말고, 승인 완료된 건이라는 안내를 보여 주세요.
>
> **개발자:** 거부된 요청은 기존 발주 상태와 승인 처리 횟수를 바꾸지 않도록 하겠습니다.
>
> **설계 담당자:** 서버가 DB에서 읽은 현재 상태로 판단하겠습니다. 승인 완료라면 저장 전에 거부하고, 화면에는 거부 이유를 표시하겠습니다.

**합의 결과:** 관리자도 승인 대기 발주만 승인할 수 있습니다. 재승인은 `409`로 거부하고 기존 상태·처리 횟수를 유지합니다.

**구현 방침:** 기존 역할 검사에 현재 상태 검사를 추가하고, 거부된 요청은 저장하지 않습니다.

이제 담당자와 정한 상태 규칙을 AI에게 전달합니다. 역할 검사와 회사 차단은 유지하고,
상태 제한이 이미 있다면 확정한 기준에 맞는지 확인한 뒤 필요한 부분만 보완합니다.

## AI에게 현재 상태 검사를 요청합니다

```text
AGENTS.md와 README.md를 읽고 같은 발주가 다시 승인되는 원인을 조사하세요.
변경할 파일과 이유를 짧게 알린 뒤 회의에서 확정한 다음 규칙을 구현하세요.

- DB에서 읽은 현재 상태로 판단하고, 승인 대기 발주만 승인할 수 있게 하세요.
- 그 밖의 상태에 새 승인 요청이 오면 409와 '승인 대기 발주만 승인할 수 있습니다.'로 거부하세요.
- 거부 후 발주 상태와 승인 처리 횟수를 유지하세요.
- 앞에서 구현한 관리자의 승인, 조회 담당자의 승인 제한과 회사 차단을 유지하세요.

기존 승인 기능에 상태 검사만 추가하세요.
```

예상 변경 위치는 `backend/approval_rules.py`입니다.
이번에는 화면이나 DB 구조를 바꾸지 않고 기존 역할 판단에 상태 판단을 추가합니다.
상태 코드는 `PENDING`이 승인 대기, `APPROVED`가 승인 완료입니다.

## 수정 후 같은 상황을 다시 확인합니다

AI 작업 후 브라우저를 새로고침하고 **본 실습**의 **실습 데이터 초기화**를 누릅니다.
수정 전 재현으로 바뀐 데이터를 되돌리는 것이며, 수정한 코드는 유지됩니다.
초기화하면 접속도 해제되므로 **A회사 관리자로 접속**합니다.
이후 첫 승인과 두 번째 요청은 같은 발주에서 이어서 보냅니다.

1. **발주 메뉴 열기**와 **1001 상세 조회**를 차례로 누릅니다. 승인 대기, 횟수 `0`인지 확인합니다.
2. **발주 승인**을 누릅니다. 실제 응답 `200`과 승인 완료, 처리 횟수 `1`을 확인합니다.
3. **승인 요청 직접 보내기**를 눌러 같은 발주에 새 요청을 보냅니다.
4. 실제 응답 `409`와 `승인 대기 발주만 승인할 수 있습니다.`를 확인합니다.
5. 재조회된 상태는 승인 완료, 처리 횟수는 `1`로 유지되는지 확인합니다.

`409`는 현재 상태와 요청이 충돌한다는 응답입니다. 상태가 계속 승인 완료여도
처리 횟수가 늘었다면 다시 처리한 것입니다. 두 값을 함께 봐야 회의에서 정한 기준을 확인할 수 있습니다.

Chapter 3의 멱등성은 같은 요청을 재전송해도 추가 처리하지 않는 성질입니다.
이번 직접 요청 버튼은 매번 새 요청을 보냅니다. 다른 직원이 같은 발주에 새 요청을 보내도
이미 끝난 승인을 다시 처리하지 않는 것이 이번 회의에서 추가한 기준입니다.

## 추가한 상태 검사와 DB 저장을 연결합니다

```text
AGENTS.md와 최신 코드를 읽고 이번에 추가한 상태 검사와 저장의 연결을 안내해 주세요.
상태 판단에 쓰는 값이 DB에서 오는 곳과, 승인 완료 발주를 저장 전에 거부하는 조건을 찾으세요.
역할 검사는 유지됐는지, 거부하면 상태·처리 횟수 갱신으로 진행하지 않는지 설명하세요.
확인할 파일·함수·검색어를 짧게 적고, 찾지 못한 곳은 미확인으로 표시하세요.
코드 조사만 하고 파일 수정이나 명령 실행은 하지 마세요.
```

4.2에서 확인한 저장 처리에 앞서, 새 상태 조건이 어디에 추가됐는지 실제 코드를 엽니다.
**DB의 현재 상태 → 승인 가능 여부 판단 → 통과한 경우 저장**을 연결해 보세요.

제공된 저장 코드는 조회·검사·저장을 하나의 트랜잭션으로 묶습니다. 트랜잭션은 여러 DB 작업을
하나의 처리 단위로 묶는 방법입니다. 상태와 횟수를 함께 바꾸고, 저장할 때 조회했던 값이
그대로인지도 조건으로 확인합니다. 이번에는 이 구조를 유지하며 상태 판단만 추가합니다.
이번에는 순서대로 보낸 두 요청을 확인했습니다. 동시에 들어온 두 요청과 DB 함수 수준의 재검증은 Day 12에서 이어서 다룹니다.

## AI 검증과 완료

수정 후에는 첫 승인만 `200`으로 성공하고, 새 재승인 요청은 `409`로 거부되어야 합니다.
두 번째 요청 뒤에도 승인 완료·처리 횟수 `1`이면 추가 승인이 반영되지 않은 것입니다.
앞에서 본 결과와 비교하고 아래 프롬프트를 그대로 실행합니다.

```text
AGENTS.md를 읽고, 상태 규칙을 추가한 본 실습에서
다음 동작이 지켜지는지 직접 확인해 주세요.

1. A회사 관리자가 자기 회사의 승인 대기 발주를 승인하면
   승인 완료로 바뀌고, 승인 처리 횟수는 1이어야 합니다.
2. 같은 발주에 새 승인 요청을 보내면 거부되고,
   승인 완료 상태와 처리 횟수 1이 유지되어야 합니다.
3. 조회 담당자는 자기 회사 발주를 볼 수 있지만 승인할 수 없어야 합니다.
4. A회사 관리자도 B회사 발주를 승인할 수 없어야 합니다.

코드는 수정하지 마세요.
확인한 결과와 확인하지 못한 항목을 짧게 알려 주세요.
이미 승인한 발주를 다시 처리하지 못하게 막는 코드 한 곳도 짚어 주세요.
```

AI가 짚어 준 상태 검사 코드를 엽니다. DB에서 읽은 상태가 승인 완료이면 저장 전에
거부하는지 확인합니다. 이번 검사는 같은 요청의 재전송이 아니라 같은 발주에 보낸 새 요청을 대상으로 합니다.

- [ ] 첫 승인 200 뒤 새 승인 요청은 409로 거부되고, 승인 완료·횟수 `1`이 유지됐습니다.
- [ ] AI가 안내한 코드에서 DB의 현재 상태를 검사하고 저장 전에 재승인을 거부하는지 확인했습니다.

**이번에 배운 것:** 권한이 있는 사용자라도 현재 업무 상태에 따라 요청을 거부해야 합니다.
