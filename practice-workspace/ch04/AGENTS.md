# Chapter 4 작업 규칙

- 실습 1은 비교 구현 실행과 질문 검토만 수행한다. 읽기 범위는 작업 지침, README.md와 lessons/01_requirement.md다. 후속 lessons·코드·검증 도구는 조사하지 않고 파일도 수정하지 않는다.
- 실습 2의 수정 허용 파일은 backend/approval_rules.py와 frontend/approval-action.js뿐이다.
- 실습 2는 해당 프롬프트에서 확정한 역할 규칙만 구현한다. 상태 제한은 실습 3에서 추가한다.
- 실습 2 생성 프롬프트는 이 범위의 구현을 승인한 요청이다. 변경 파일과 이유를 짧게 보고하고 구현한다.
- 실습 3은 실습 2 완료 코드에 backend/approval_rules.py의 현재 상태 검사만 추가한다.
- 실습 3 생성 요청도 해당 범위의 구현 승인이다. 역할 검사를 보존하고 상태는 DB 조회 값으로 판단한다.
- 실습 3에서 화면·저장소·직접 요청 장치나 _starter/를 수정하지 않는다. 새 요청 키도 추가하지 않는다.
- 실습 1~3에서 결함 전용 모듈을 읽어 다음 정책의 답을 가져오거나 수정하지 않는다.
- 실습 4는 먼저 읽기 전용으로 요청·사용자 회사·조회·판단·저장 흐름을 추적한다.
- 실습 4의 최소 수정 요청은 backend/defect_scope.py만 허용한다. 서버 세션의 회사로 조회를 제한한다.
- 결함 공간의 고정 역할·상태 검사와 저장 흐름, 본 실습 구현을 바꾸지 않는다.
- 실습 4 수정 프롬프트는 해당 범위의 구현 승인이다. 초기화는 코드를 되돌리지 않는다.
- 범위 밖 변경이 필요하면 수정 전에 이유를 보고한다.
- 먼저 이 파일과 README.md를 읽고 현재 단계와 허용 범위를 확인한다. 업무 정책의 근거는 현재 실습의 요구사항과 확정 답변이며, 작업 지침으로 정책의 빈칸을 채우지 않는다.
- 독자 AI는 서버·저장소·세션·관찰 화면·전송기·초기화·실행 환경을 수정하지 않는다.
- 이 지침은 키트 제작자의 승인된 구현 작업과 독자 실습의 변경 경계를 구분한다.
- 역할·상태·회사 검사나 완성 답안을 요청 없이 미리 추가하지 않는다.
- inputs/는 기존 비교 자료다. 수정하거나 실행형 실습의 확정 정책으로 사용하지 않는다.
- 다른 Chapter와 reference-app은 읽거나 수정하지 않는다.
- 실제 사용자 정보·비밀정보·운영 DB를 사용하지 않는다.
- 사용자의 회사·역할은 서버 세션을 기준으로 하고 요청값으로 대체하지 않는다.
- 관찰 값은 실제 응답과 DB 재조회로 확인한다. 화면 표시를 조작해 성공처럼 만들지 않는다.
- 실습 2 이후 검증 시 python verify_observation.py를 실행한다. 보고는 변경 범위, 실제 실행 결과, 미확인 항목 순서로 짧게 작성하며 코드 확인과 실행을 구분한다.
- 실습 4 완료 후 선택 검증은 .venv/Scripts/python.exe verify_business_rules.py로 실행한다. 임시 사본만 사용하며 시작본·중간 단계에 완성 기준 통과를 요구하지 않는다.
- verify_business_rules.py는 제공된 검사 도구다. 독자 AI는 수정하지 않으며, 실패를 감추기 위해 업무 기대값을 바꾸지 않는다.
- 검사 기준이나 도구를 수정해 검증 실패를 감추지 않는다.
- _starter/는 누적 변경 비교용 시작 기준본이다. 수정하지 않는다.
- 승인 정책은 가상 회사의 학습 정책이며 실제 ERP의 역할 계약으로 설명하지 않는다.
- 결함 공간은 회사 범위 조회만 빠진 비교 구현이다. 실제 데이터가 없는 로컬 실습에만 사용한다.
- 본 실습의 비교 동작, 역할·상태 완료 코드, 결함 시작본·수정본의 검증 기준을 구분한다.
