# Chapter 11 작업 규칙

- `workspace/erp-project/`와 `workspace/frontend-project/`만 수정한다.
- DB, API, 화면을 한 단계씩 연결하고 각 단계의 결과를 확인한 뒤 다음 단계로 이동한다.
- Chapter 10 파일을 복사하지 않고, Chapter 11 scaffold에서 시작한다.
- 완료 뒤 폴더 이름을 바꾸거나 Day 프로젝트로 재사용하지 않는다.

## 고정 실습의 작업 순서

- 먼저 [연결 명세](connection_spec.md), 현재 단계의 하위 `AGENTS.md`와 시작 파일을 읽습니다. 명세 파일은 작업 중 수정하지 않습니다.
- Chapter 11의 명시적인 생성·구현 요청에는 다음 장별 예외를 적용합니다. 상위 공통 지침의 별도 조사 보고·승인 절차 대신, 요청받은 한 단계의 조사·구현·검사를 한 요청 안에서 진행합니다.
- DB 단계는 생성 SQL을 답변으로 제공하고, API·화면 단계는 명세의 허용 위치 안에서 최소 변경을 적용합니다. 아직 요청하지 않은 다음 단계는 구현하지 않습니다.
- 독자가 조사만 요청하거나 `아직 수정하지 마세요`라고 명시하면 조사 결과만 보고하고 멈춥니다. 이 규칙은 현재 원고의 조사 전용 프롬프트에도 적용합니다.
- 명세 누락, 현재 구현·SQL 실행본과의 충돌, 범위 밖 파일·의존성 변경이나 개인 작업 덮어쓰기가 필요하면 적용 전에 차이·이유·최소 변경안을 보고하고 확인을 기다립니다.
- 다른 Chapter에는 이 예외를 적용하지 않습니다. 실제 DB 실행·승인 요청·비밀값 접근과 관찰값 작성은 여전히 AI 작업 범위 밖입니다.

## 생성·검토와 기록의 경계

- 구현 전에 관련 파일·현재 명세·이번 단계의 변경 범위를 조사하고, 위 작업 순서에 따라 적용한다.
- 적용 뒤 변경 파일·검사 결과·실행을 막는 문제를 짧게 보고한다. 별도 확인이 필요한 경우는 위 예외 중단 조건을 따른다.
- observation_record.md는 독자의 실제 관찰 기록이다. 읽기만 하며 실제 관찰값이나 실행 판정을 대신 작성하지 않는다.
- 검토 요청에서는 코드·SQL·관찰 기록을 수정하지 않는다. 업무 요청이 구현된 위치를 현재 상대 경로·행 번호, 핵심 코드 몇 줄과 쉬운 설명으로 안내하고 실제 관찰값과 연결한다.
- Chapter 11의 구현 확인 안내에는 상위 공통 보고의 근거표 대신 업무 항목별 짧은 설명을 사용한다. 실제 파일에서 찾지 못한 위치는 만들지 않고, 코드 확인과 직접 실행한 확인을 구분한다.
- 독자가 요청한 업무 보고는 관찰 기록의 실제 사실로 대화에 초안을 작성할 수 있다. 기록 파일은 수정하지 않으며 미실행 결과를 검증했다고 표현하지 않는다.
- 원인 조사에서는 실제 코드 위치를 근거로 확인된 사실과 원인 후보를 구분한다. 관찰값이나 SQL 적용 여부가 불확실하면 필요한 확인 한 가지를 안내하고, 원인 확인 전 전체 초기화·참조 코드 교체를 제안하지 않는다.
- 검토에서 기록과 구현이 다르거나 근거가 없으면 해당 쟁점과 필요한 확인만 안내한다. 추가 개선 과제나 전체 실험 재실행은 요구하지 않는다. DB 직접 호출의 취소 결과를 API rollback 실행의 검증으로 해석하지 않는다.
- SQL 실행본은 workspace/erp-project/sql/에서 번호순으로 읽는다. 보존본 검토와 DB에 실제 적용됐다는 확인을 구분한다.
- 실제 .env·비밀값 읽기·출력과 DB 접속은 하지 않는다. SQL과 브라우저 실습은 독자가 직접 수행한다.
- 실행한 검사, Fail, Not Run과 테스트 없음을 구분한다. 자동 테스트·실행 기록 없이 성공을 추정하지 않는다.
