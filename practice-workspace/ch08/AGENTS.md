# Chapter 8 작업 규칙

<!-- common-rules-version: chapter8-v5 -->

## 공통 작업 순서 (approval-required)

1. 이 파일과 `README.md`, 작업 대상이 `project/`라면 `project/AGENTS.md`까지 먼저 읽는다.
   업무 조건은 `chapter8_order_spec.md`에서 요청받은 단계와 그 단계가 의존하는 앞 단계 항목을 확인한다.
2. 요구사항, 기존 파일, 변경 범위와 검증 방법을 먼저 보고한다.
3. 독자의 승인을 받은 뒤 승인된 범위만 최소 변경한다.
4. 변경 파일과 실행한 검증, 실행하지 못한 검증을 구분해 보고한다.

## 보안과 변경 범위 (secrets-protected)

- `.env`, 비밀번호, API key, JWT와 실제 DB URL을 읽거나 출력하지 않는다.
- 현재 Chapter 밖의 파일과 이미 완성한 이전 단계의 결과를 요청 없이 수정하지 않는다.
- `database.py`, `models.py`, `practice_db.py`, 공개 환경 예시와 `_starter/`는 시작 파일이므로 보존한다.
- 요청받지 않은 후속 단계의 완성 코드를 미리 생성하지 않는다.

## 검증 판정 (evidence-scoped)

- 결과는 `Pass`, `Fail`, `Not Run`, `테스트 없음`으로 구분한다.
- 코드 검토와 실제 명령 실행을 같은 근거로 취급하지 않고 근거 유형을 함께 밝힌다.
- 테스트를 실행하지 않았다면 통과로 추정하지 않는다.
- 검증 요청의 보고는 확인할 질문·판정·근거의 표로 한다. 근거 출처는 AI가 직접 명령을 실행했으면
  `AI 실행:`, 독자가 제공한 실행 결과를 확인했으면 `독자 제공 실행 결과:`, 파일만 읽었으면
  `코드 검토:`로 시작한다. 독자 제공 결과를 AI가 직접 실행한 결과로 표시하지 않는다. `Fail`·`Not Run`·`테스트 없음` 항목은 표 아래에
  원인과 다음 확인 방법을 쓰고, 독자가 직접 확인할 최소 코드 한 곳을 지정한다.
- Mock 검증은 전달값·호출·오류 전파의 근거이며 실제 DB 저장·롤백·HTTP 성공의 근거가 아니다.

## Chapter 8 역할

문서마다 다음 역할을 맡는다. 다른 세션에서도 이전 대화 대신 이 문서와 실제 파일을 확인한다.

| 문서 | 확인할 내용 |
|---|---|
| [project/AGENTS.md](project/AGENTS.md) | 구현 위치와 공개 클래스·함수 이름, 변경·보존 범위 |
| [chapter8_order_spec.md](chapter8_order_spec.md) | 단계별 입력·업무 규칙·저장 조건·완료 기준 |
| [ai_build_rules.md](ai_build_rules.md) | 조사·계획·승인·구현·테스트의 공통 작업 지침 |
| [ai_review_rules.md](ai_review_rules.md) | 실제 근거와 실행 여부에 따른 검토·보고 기준 |

- `project/`만 Chapter 8의 구현 루트로 사용한다.
- 발주 한 건을 요청 검증, 업무 판단과 저장 계획, 트랜잭션 저장, API 연결
  네 부분으로 나누어 만든다. 요청 검증과 업무 판단은 DB 없이 실행되는 값 중심 코드이고, 저장 함수가
  발주 마스터·상세·감사 기록을 한 트랜잭션으로 저장한다.
- 8.2~8.3에서 요청 검증과 업무 판단을 먼저 완성하고, 8.4에서 저장, 8.5에서 API 연결을 추가한다.
- 역할은 요청 검증·업무 판단·저장·API 연결의 실제 동작으로 설명한다.
- 공개 클래스·함수 이름과 위치는 `project/AGENTS.md` 규약을 유지한다.
- 세부 업무 조건과 필수 검사는 `chapter8_order_spec.md`를 따른다. 이 파일에 별도로 복제하지 않는다.
- Core는 키트의 로컬 SQLite에서 정상 발주 한 건을 실행한다. 실제 PostgreSQL이나 Supabase 연결은 Core에 포함하지 않는다.
- 발주 마스터·상세·감사만 저장하며 상품 단가·활성 상태를 변경하지 않는다.
  실습에 없는 모델·업무 규칙을 추가하지 않고, 클라이언트가 보낸 회사·상태·단가·합계를 신뢰하지 않는다.
- 교육용 `POST /franchise/order`를 실제 제품의 `POST /api/v1/purchase_orders`와 같은 경로·보장이라고
  설명하지 않는다. JWT, 멱등성, 소유권, 마감과 PostgreSQL 동시성 제어는 Core 범위가 아니다.
