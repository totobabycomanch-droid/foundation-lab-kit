# 실습 2 — 역할: 조회할 수 있으면 승인해도 되나요?

## 이번에 만드는 것

첫 회의에서 정한 역할 규칙을 구현하고, 그 결과를 직접 볼 화면도 만듭니다.

> **업무 담당자:** 회사 관리자만 자기 회사 발주를 승인할 수 있습니다. 조회 담당자는 자기 회사 발주를 볼 수 있어야 합니다.
>
> **개발자:** 먼저 서버에서 승인 권한을 확인하겠습니다. 이어서 조회와 승인 결과를 보여 줄 화면을 만들겠습니다.
>
> **설계 담당자:** 화면의 승인 버튼 제한과 서버의 승인 거부를 따로 확인할 수 있게 하겠습니다.

**확정된 업무 기준:** 조회 담당자는 조회할 수 있고, 승인은 회사 관리자만 할 수 있습니다.

이번 실습은 두 요청으로 나눕니다. 먼저 승인 권한을 구현하고, 다음에 제공 API를 호출하는
Vue 확인 화면을 만듭니다. 화면은 이후 상태 검사와 회사 경계 확인에서도 계속 사용합니다.

## 제공 기능과 이번에 만들 기능을 구분합니다

서버 실행, 사용자·발주 데이터, DB 저장·초기화, API는 키트가 제공합니다.
독자는 AI와 업무 판단 및 화면을 구현합니다. AI가 보고한 변경 파일을 아래 표와 비교하세요.
표는 조사 결과를 확인하는 기준이며 프롬프트에 파일 전문을 붙여 넣는 과제가 아닙니다.

| 실습 | 학습자 작업 위치 | 바꿀 내용 |
|---|---|---|
| 4.1 | 없음 | 업무 회의와 확정된 기준 읽기 |
| 4.2 권한 구현 | `backend/approval_rules.py` | 서버의 역할 검사 |
| 4.2 화면 생성 | `frontend/app.js`, `frontend/approval-action.js` | 조회·승인·응답·DB 재조회 표시 |
| 4.3 | `backend/approval_rules.py` | 현재 상태 검사 추가 |
| 4.4 화면 연결 | `frontend/app.js` | 결함 실습 선택과 B회사 대상 요청 |
| 4.4 회사 조건 수정 | `backend/defect_scope.py` | 승인 대상 조회의 회사 범위 |

`backend/app.py`는 제공 API와 화면 파일을 연결하고, `backend/store.py`는 DB 저장을 담당합니다.
`frontend/transport.js`는 실제 HTTP 응답을 전달합니다. 이 기반은 그대로 사용합니다.
`_starter/`는 비교·복구용 시작 코드입니다. 지금의 `frontend/app.js`에는 생성 안내만 있습니다.

## AI에게 승인 권한을 구현하게 합니다

첫 프롬프트는 서버의 승인 권한만 구현합니다. 이 요청을 마쳐도 브라우저에는 아직 시작 안내가 보입니다.

```text
AGENTS.md와 README.md를 읽고 현재 발주 승인 기능을 조사하세요.
변경할 파일과 이유를 짧게 알린 뒤 다음 기준으로 서버의 승인 권한을 구현하세요.

- 회사 관리자만 자기 회사 발주를 승인할 수 있습니다.
- 조회 담당자는 자기 회사 발주를 조회할 수 있지만, 직접 승인 요청은 403으로 거부합니다.
- 거부된 요청은 발주 상태와 승인 처리 횟수를 바꾸지 않아야 합니다.

이번에는 승인 권한만 구현하고, 기존 회사 차단은 유지하세요.
```

AI가 `backend/approval_rules.py`에서 역할을 검사했는지 확인합니다.
회사와 역할은 서버가 확인한 사용자 정보이고, 발주 상태는 DB에서 읽은 값입니다.

## AI에게 확인 화면을 만들게 합니다

이제 방금 구현한 기능을 브라우저에서 확인할 화면을 만듭니다. 화면의 모양은 조금 달라도
아래 항목과 버튼 이름이 있으면 책의 확인 절차를 따라갈 수 있습니다.

| 화면에 표시할 것 | 독자가 확인할 내용 |
|---|---|
| 현재 사용자·회사·역할 | 누구의 권한으로 요청하는가? |
| 발주 목록·상세 | 어느 발주이고 현재 상태·처리 횟수는 무엇인가? |
| 실제 서버 응답 | 승인 요청이 성공했는가, 거부됐는가? |
| 요청 후 다시 조회한 발주 | 실제 저장된 상태·처리 횟수가 바뀌었는가? |

```text
AGENTS.md와 README.md를 읽고, 방금 구현한 발주 승인 기능을
브라우저에서 확인할 Vue 3 화면을 만들어 주세요. 제공된 API·스타일·응답 전달 함수를 사용하세요.

- A회사 조회 담당자, A회사 관리자, B회사 관리자로 접속하는 버튼을 만드세요.
  버튼 이름은 각각 'A회사 조회 담당자로 접속', 'A회사 관리자로 접속', 'B회사 관리자로 접속'입니다.
- 서버에서 받은 현재 사용자·회사·역할과 자기 회사 발주 목록을 보여 주세요.
- '발주 메뉴 열기'와 '1001 상세 조회'처럼 발주 번호가 들어간 상세 버튼을 제공하세요.
  상세에는 발주 상태와 승인 처리 횟수를 표시하세요.
- '발주 승인'은 조회 담당자에게 제한하고 '조회 담당자는 발주를 승인할 수 없습니다.'를 표시하세요.
  별도의 '승인 요청 직접 보내기'는 조회 담당자도 눌러 서버의 거부를 확인할 수 있게 하세요.
- '실제 서버 응답'에는 승인 요청의 실제 HTTP 코드와 본문을 표시하세요.
  요청 후 발주를 다시 조회해 상태·횟수를 갱신하고, 승인 응답은 함께 유지하세요.
- '실습 데이터 초기화'와 '상태 다시 조회'를 제공하세요.
  사용자를 바꾸거나 초기화하면 이전 발주·응답을 정리하고, 요청 중에는 중복 행동을 제한하세요.

이번에는 본 실습 화면만 만듭니다. 서버의 업무 규칙은 유지하세요.
```

AI가 `frontend/app.js`와 `frontend/approval-action.js`를 만들거나 수정했는지 확인하고
브라우저를 새로고침합니다. 시작 안내 대신 사용자 선택·발주·응답 화면이 보여야 합니다.
화면 생성이 끝나면 **실습 데이터 초기화**를 누릅니다.

## 직접 확인합니다

**조회 담당자의 조회와 승인 거부**

1. **A회사 조회 담당자로 접속**하고 **발주 메뉴 열기**를 누릅니다.
2. **1001 상세 조회**에서 승인 대기·처리 횟수 `0`인지 확인합니다.
3. **발주 승인**이 제한되고 '조회 담당자는 발주를 승인할 수 없습니다.'가 표시되는지 확인합니다.
4. **승인 요청 직접 보내기**를 누르고 **실제 서버 응답**에서 `403`을 확인합니다.
5. 다시 조회된 1001번이 승인 대기·처리 횟수 `0`을 유지하는지 확인합니다.

**관리자의 정상 승인**

1. **A회사 관리자로 접속**하고 **발주 메뉴 열기 → 1001 상세 조회**를 선택합니다.
2. **발주 승인**을 눌러 `200`, 승인 완료·처리 횟수 `1`을 확인합니다.



`403`은 승인 권한이 없다는 응답입니다. 화면에서 버튼을 제한해도 서버에 직접 요청할 수
있으므로 두 결과를 따로 봅니다. 응답 표시는 요청의 결과이고, 발주 상태·횟수는 서버에서
다시 읽은 DB 값입니다. 이 둘이 함께 있어야 거부 후 데이터도 유지됐는지 알 수 있습니다.

## 서버가 승인 기준을 지키는 곳을 찾습니다

```text
AGENTS.md와 최신 코드를 읽고, 조회 담당자의 요청을 저장 전에 거부하는
역할 검사 코드 한 곳을 짚어 주세요. 그 조건과 DB 저장이 연결되는 순서도 쉽게 설명해 주세요.
코드는 수정하지 마세요.
```

AI가 안내한 실제 파일을 열고 **사용자 확인 → 역할 판단 → DB 저장**을 확인합니다.
함수의 한글 docstring을 함께 읽으면 입력값의 출처와 거부 후 흐름을 이해하는 데 도움이 됩니다.

## AI 검증과 완료

화면에서 본 동작을 AI가 실제 요청과 코드로 다시 확인합니다. 생성한 화면이 응답을
제대로 보여 주는지와, 화면의 버튼 제한을 거친 경우와 직접 요청한 경우를 함께 살펴봅니다.

```text
AGENTS.md를 읽고, 본 실습에서 다음 동작이 지켜지는지 직접 확인해 주세요.

1. A회사 조회 담당자는 자기 회사 발주를 볼 수 있어야 합니다.
2. 조회 담당자가 직접 승인 요청을 보내면 거부되고, 발주 상태와 처리 횟수는 유지되어야 합니다.
3. A회사 관리자는 자기 회사 발주를 승인할 수 있어야 합니다.
4. A회사 관리자도 B회사 발주를 승인할 수 없어야 합니다.
5. 화면의 승인 응답과 다시 조회한 상태·횟수가 실제 서버 결과와 일치해야 합니다.

코드는 수정하지 마세요. 확인한 결과와 확인하지 못한 항목을 짧게 알려 주세요.
조회 담당자의 승인을 막는 코드 한 곳도 짚어 주세요.
```

AI는 `python verify_observation.py`로 제공 파일도 확인합니다. 이 검사는 제공 기반과
시작 기준본을 보호하며, 독자가 생성한 `frontend/app.js`의 변경은 허용합니다.
업무 규칙과 화면 동작은 별도로 확인합니다. `Pass`는 실제 실행해 기준을 만족한 경우,
`Fail`은 실행했지만 기준과 다른 경우, `Not Run`은 실행하지 못한 경우입니다.

- [ ] 직접 만든 화면에서 조회 담당자의 조회·승인 거부와 관리자의 정상 승인을 확인했습니다.
- [ ] 승인 응답과 다시 조회한 상태·횟수를 구분하고, 역할 검사가 DB 저장보다 먼저 실행되는지 확인했습니다.

**이번에 배운 것:** 기능을 확인할 화면도 AI와 만들 수 있습니다. 화면의 안내와 서버 응답, DB 값을 함께 비교해 업무 규칙을 판단합니다.
