# 실습 2 — 조회할 수 있으면 승인할 수 있나요?

실습 1의 업무 회의에서 정한 역할 규칙을 구현합니다.

> 회사 관리자만 자기 회사 발주를 승인할 수 있습니다. 조회 담당자는 자기 회사 발주를 조회할 수 있습니다.

시작본에는 역할 제한이 없습니다. 본 실습을 초기화한 뒤 아래 요청으로 회의에서 정한 기준을 구현합니다.

```text
AGENTS.md와 README.md를 읽고 승인 요청·사용자 확인·저장 흐름을 조사하세요.
변경할 파일과 이유를 짧게 알린 뒤 회의에서 확정한 다음 기준을 구현하세요.

- 서버가 확인한 회사 관리자만 자기 회사 발주를 승인할 수 있습니다.
- 조회 담당자는 메뉴와 발주를 조회할 수 있습니다.
- 조회 담당자의 발주 승인 버튼은 제한하고 이유를 표시하세요.
- 직접 승인 요청도 서버에서 403으로 거부하고 발주 상태·처리 횟수를 유지하세요.

수정 범위는 AGENTS.md의 실습 2입니다. 화면 배치·스타일과 기존 회사 차단은 유지하세요.
상태 제한은 다음 실습에서 추가합니다. 변경 파일·실행 결과·미확인 항목을 짧게 보고하세요.
```

## 직접 확인

AI 작업 후 브라우저를 새로고침합니다. 초기화 후의 1001번은 승인 대기, 처리 횟수 0입니다.

1. A회사 조회 담당자로 접속하고 발주 메뉴를 엽니다.
2. 1001번 상세에서 일반 승인의 제한과 이유를 확인합니다.
3. 승인 요청 직접 보내기를 눌러 403을 확인합니다.
4. 1001번이 승인 대기, 처리 횟수 0인지 확인하고 상세를 다시 조회합니다.
5. A회사 관리자로 바꾸어 메뉴·1001번 상세를 열고 승인합니다.
6. 200, 승인 완료, 처리 횟수 1을 확인합니다.

## 코드를 따라 확인

이 키트의 메뉴 진입은 접속한 사용자가 있는지만 확인하며 역할별로 제한하지 않습니다.
두 역할의 메뉴·조회를 유지하고 서버의 승인 처리에서 역할을 검사합니다.
역할별 메뉴 권한 설정은 이후 Day에서 다룹니다.
아래 요청으로 메뉴 조건과 승인 요청의 실제 흐름을 확인합니다.

```text
AGENTS.md와 최신 코드를 읽고 역할 검사를 안내해 주세요.
1. 메뉴: 접속 여부만 확인하는 위치를 찾으세요. 역할별 메뉴 검사는 없습니다.
2. 승인: 요청 전송 → 사용자 확인 → 회사 조회 → 역할 검사 → 저장 → 응답 순서를 보여 주세요.
3. 거부: 조회 담당자가 멈추는 곳과 관리자가 저장으로 진행하는 곳을 표시하세요.
각 단계의 파일·함수·검색어를 한 줄로 적고, 찾지 못한 곳은 미확인으로 표시하세요.
코드 조사만 하고 파일 수정이나 명령 실행은 하지 마세요.
```

경로와 검색어를 따라 사용자 정보의 출처, 역할 검사의 거부 위치, DB 저장 위치를 찾아갑니다.
거부된 요청이 저장에 도달할 수 있는지 설명해 봅니다. 모든 문법을 해석할 필요는 없습니다.

## AI 검증과 완료

조회 담당자의 직접 승인은 `403`으로 거부되고, 발주는 승인 대기·처리 횟수 `0`을
유지해야 합니다. 관리자의 승인은 `200`이고, 승인 완료·처리 횟수 `1`이어야 합니다.
앞에서 본 화면과 비교한 뒤 아래 프롬프트를 그대로 실행합니다. 별도 기록은 작성하지 않습니다.

화면에서 확인한 동작을 AI가 실제 요청과 코드로 다시 살펴봅니다. 버튼은 막혔지만
서버에서는 승인을 허용하는 경우나, 요청한 범위 밖의 코드를 바꾼 문제를 확인하기 위한 과정입니다.

```text
AGENTS.md를 읽고, 본 실습에서 다음 동작이 지켜지는지 직접 확인해 주세요.

1. A회사 조회 담당자는 자기 회사 발주를 볼 수 있어야 합니다.
2. 조회 담당자가 화면의 승인 제한을 거치지 않고 직접 요청해도
   승인은 거부되고, 발주 상태와 승인 처리 횟수는 바뀌지 않아야 합니다.
3. A회사 관리자는 자기 회사 발주를 승인할 수 있어야 합니다.
4. A회사 관리자도 B회사 발주를 승인할 수 없어야 합니다.

코드는 수정하지 마세요.
확인한 결과와 확인하지 못한 항목을 짧게 알려 주세요.
조회 담당자의 승인을 막는 코드 한 곳도 짚어 주세요.
```

제공 파일의 변경 여부는 AI가 현재 `ch04`에서 `python verify_observation.py`로 검사합니다.
이 검사는 Python 기본 기능만 쓰므로 일반 `python`으로 실행합니다. 통과는 제공 파일이
그대로라는 뜻입니다. 업무 동작은 별도로 확인해야 하며, 실패하면 표시된 파일을 확인합니다.
검사를 통과시키려고 검사 기준을 바꾸지는 않습니다.

AI가 짚어 준 역할 검사 코드를 엽니다. 조회 담당자의 요청을 거부하면 그 뒤의
상태·처리 횟수 저장으로 진행하지 않는지 확인합니다.

- [ ] 조회 담당자는 조회할 수 있고 직접 승인은 403으로 거부되며, 상태·횟수는 유지됐습니다. 관리자는 정상 승인했습니다.
- [ ] AI가 안내한 코드에서 역할 검사가 저장보다 먼저 실행되는지 확인했습니다.

**이번에 배운 것:** 메뉴를 열고 조회할 수 있어도 승인할 수 있는지는 서버에서 별도로 확인해야 합니다.
