# Chapter 3 발주 등록 실습 규칙

## 작업 범위

- 현재 `ch03` 안에서만 작업한다. 다른 Chapter와 `reference-app`은 수정하지 않는다.
- 정상 저장·중복 클릭 실습에서 수정 가능한 파일은 `backend/order_write.py`, `frontend/order-form.js`다.
- 서버 재전송 실습에서는 `backend/order_replay.py`도 수정할 수 있다. 앞선 두 실습에서는 수정하지 않는다.
- 회사별 조회 실습에서는 `backend/company_read.py`만 수정한다. 앞선 저장·재전송 코드는 유지한다.
- 서버, 저장소, 관찰 화면, 스타일, 실행 스크립트와 의존성은 제공된 실습 장치다. 수정하지 않는다.
- 구현 전에 현재 파일과 README를 읽고 변경할 파일과 이유를 두 문장 이내로 보고한다.
- 원고의 생성 프롬프트는 해당 단계의 구현을 승인한 요청이다. 범위 안에서는 구현까지 진행한다.
- 요청하지 않은 다음 단계의 기능을 미리 구현하지 않는다.
- 긴 조사 보고서나 별도 결과표를 만들지 않는다.

## 연결 규약

- FastAPI와 Vue 3를 사용한다. Vue는 npm으로 설치한 브라우저용 모듈을 서버가 제공한다.
- POST `/api/orders`: `{"item_name":"커피 원두","quantity":2}`를 받아 저장 결과를 반환한다.
- 입력 모델은 `backend/models.py`의 `OrderInput`이다. 공백뿐인 품명과 1~9999 밖 수량은 거부한다.
- `backend/order_write.py`의 기존 라우트에서 `request.app.state.store.add_order(order)`를 호출하면
  SQLite에 저장된 `id`, `item_name`, `quantity`를 받는다. 연결 규약이며 저장소 자체는 변경하지 않는다.
- 프론트엔드는 `/vendor/vue.js`에서 Vue를 import한다. `frontend/order-form.js`는 이름이
  `OrderForm`인 Vue 컴포넌트를 export한다. 정해진 내부 변수명은 없다.
- 폼의 저장 요청은 제공된 `frontend/order-transport.js`의 `sendOrder(order)`를 사용한다.
  이 함수는 새 요청 키와 요청 본문을 보관해 전송하고 fetch의 Response를 반환한다.
  직접 fetch로 저장하거나 관찰기 값을 폼에서 변경하지 않는다. 전송기 자체는 수정하지 않는다.
- 새 저장마다 새 UUID 키를 사용한다. 오른쪽 재전송 버튼만 마지막 키와 본문을 그대로 재사용한다.
- API 오류 메시지는 FastAPI의 `detail` 또는 간단한 한국어 안내로 표시한다.
- 화면 관찰기는 별도 요청으로 서버 수치와 저장 목록을 갱신하므로 이벤트로 목록을 조작하지 않는다.

## 화면 기준

- 품명·수량의 label과 입력을 연결하고 저장 버튼을 제공한다.
- 입력은 품명 1~80자, 정수 수량 1~9999다. 서버도 입력을 검사한다.
- 성공 안내는 `role="status"`, 오류 안내는 `role="alert"`로 표시한다.
- 제공된 CSS를 사용한다. 폼에는 `order-form`, 각 입력 묶음에는 `field`를 사용할 수 있다.
- 첫 실습은 정상 저장만 구현한다. 두 번째 실습에서 저장 중 중복 행동 방지를 추가한다.
- 두 번째 실습에서는 버튼 표시뿐 아니라 저장 처리 진입 시에도 중복 실행을 막는다.
- 성공과 실패 모두 저장 중 상태를 해제한다. 실패 시 입력을 보존한다.

## 서버 재전송 실습

- 이 단계에서만 저장 API가 `Idempotency-Key`를 읽고 `save_order_once(store, order, request_key)`를 호출한다.
- 키가 없거나 UUID 형식이 아니면 HTTP 400을 반환한다.
- 같은 키·같은 입력이면 발주를 추가 생성하지 않고 같은 `id`, `item_name`, `quantity`를 반환한다.
- 같은 키·다른 입력이면 HTTP 409를 반환한다. 이 예제의 입력 비교는 OrderInput으로 검증된 값을 기준으로 한다.
- 다른 키는 별도 저장 의도다. 품명과 수량이 같아도 새 발주로 저장한다.
- SQLite의 `orders`, `order_requests` 테이블은 준비되어 있다. DB 스키마는 바꾸지 않는다.
- `order_requests`는 `request_key`, `item_name`, `quantity`, `order_id`를 저장한다.
- `store.connect()`는 정상 종료 시 커밋, 예외 시 롤백하고 연결을 닫는 컨텍스트 관리자다.
- 같은 연결의 한 트랜잭션에서 키 확인, 발주 저장과 키 기록을 처리한다.
  쓰기 경합에도 같은 키로 발주가 두 건 생기지 않아야 한다. `add_order`의 별도 연결로 나누지 않는다.
- 키 기록은 DB에 남긴다. 프로세스 메모리의 사전이나 화면의 목록만으로 중복을 판단하지 않는다.
- 상태 코드는 처음 저장과 재전송 모두 201로 유지한다. 응답 본문은 위의 세 필드다.
- 초기화 버튼은 발주와 키 기록을 함께 비운다. 서버 재시작은 두 기록을 보존한다.
- 화면의 재전송 버튼, 요청 캡처, ID 표시, 집계와 저장 목록은 수정하지 않는다.
- 저장·재전송은 단일 사용자 로컬 예제다. 회사별 조회는 아래의 별도 데이터와 세션으로 실습한다.
  운영용 멱등 처리나 ERP 전체의 회사 격리로 설명하지 않는다.

## 회사별 조회 실습

- 테스트 사용자 선택과 서버 세션은 `backend/lab_auth.py`에 준비되어 있다. 수정하지 않는다.
- `POST /api/lab/login`은 허용된 `user_id`만 받아 서버의 고정 사용자 정보로 세션을 만든다.
  사용자·회사 정보를 쿠키 본문에서 직접 해석하지 않는다. 이 로그인은 로컬 테스트 사용자 선택용이다.
- `current_lab_user` 의존성이 세션을 확인하고 불변 `LabUser`를 전달한다. 세션이 없으면 401이다.
- `GET /api/lab/me`는 서버가 확인한 `user_id`, `corp_id`, `corp_name`을 반환한다.
- `backend/company_read.py`의 `GET /api/lab/orders/{order_id}`에서 전달된 `user.corp_id`로 조회를 제한한다.
- `request.app.state.store.connect()`로 SQLite에 연결한다. `company_orders`의 필드는
  `id`, `corp_id`, `item_name`, `quantity`다. ID와 사용자 회사 조건을 함께 적용해 조회한다.
- 자기 회사 발주라면 위 네 필드만 HTTP 200으로 반환한다.
- 다른 회사 발주와 존재하지 않는 발주는 모두 HTTP 404, `발주를 찾을 수 없습니다.`로 응답한다.
  오류 본문이나 다른 응답 필드에 대상 회사의 품명·수량을 넣지 않는다.
- 요청의 Query·Header에 회사가 있어도 접근 범위의 근거로 사용하지 않는다.
- 조회용 고정 데이터는 A회사 발주 1001, B회사 발주 2001이다. 테이블·데이터는 변경하지 않는다.
- 앞선 `orders`·`order_requests`는 저장·재전송 관찰용으로 별도 관리한다. 새 회사 조건을 적용하지 않는다.
- `frontend/company-probe.js`는 응답의 상태와 본문을 그대로 보여 주는 관찰 장치다. 수정하지 않는다.
- 별도 사용자 등록·실제 JWT·Supabase·회사별 쓰기·목록 조회 정책은 이번 실습에 추가하지 않는다.

## 검증과 보고

- 변경 파일을 먼저 `_starter/`의 같은 상대 경로와 비교한다. Git diff가 있으면 함께 확인한다.
- 네 실습은 각각 원고의 행동으로 확인한다. 회사별 조회는 자기 회사 성공과 다른 회사 차단을 함께 확인한다.
- 직접 확인한 결과와 실행하지 못한 항목을 구분한다. 실행하지 않은 검증은 `Not Run`으로 적는다.
- 출력은 변경 파일, 이번 규칙의 처리, 검증 결과를 합쳐 다섯 줄 이내로 한다.
- 관찰 장치나 의존성을 바꿔야 한다면 적용하지 말고 파일과 이유를 먼저 보고한다.
