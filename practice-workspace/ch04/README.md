# Chapter 4 발주 승인 실습

요구사항의 질문을 찾고 역할·상태를 구현한 뒤 회사 경계 결함을 추적하는 승인 실습이다.
본 실습은 역할·상태 제한이 없는 비교 구현으로 시작한다. 최종 정책 구현으로 오해하지 않는다.
`inputs/`의 세 파일은 이전 정적 조사 실습 자료이므로 이번 장에서는 열거나 실행하지 않는다.

## 실행

Python 3.12 이상, Node.js 22 이상을 준비하고 이 ch04 폴더를 VS Code에서 연다.
첫 설치에는 인터넷 연결이 필요하다. PowerShell에서 다음 한 명령을 실행한다.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\start_lab.ps1
```

`http://127.0.0.1:8304`로 접속한다. 종료는 해당 터미널에서 Ctrl+C다.
포트가 사용 중이면 `-Port 8305`를 붙이고 같은 포트로 접속한다.
스크립트는 이 폴더의 .venv와 node_modules에 설치한다. 실제 ERP·Supabase는 사용하지 않는다.

## 공간과 사용자

- 본 실습과 회사 경계 결함 실습은 한 서버에서 실행하지만 SQLite DB와 세션은 별개다.
- 화면 위 공간 버튼으로 전환한다. 이전 공간의 응답·선택 발주 표시는 비운다.
- 각 공간에서 A회사 조회 담당자, A회사 관리자, B회사 관리자를 선택할 수 있다.
- A·B회사는 서로 다른 회사이며, 각 회사의 조회·승인 범위를 확인하는 학습용 정책을 사용한다.
- 메뉴 진입은 접속한 사용자가 있는지만 확인한다. 역할별 메뉴 권한 검사는 없다.
- 사용자 회사·역할은 서버의 고정 매핑에서 읽는다. 사용자 선택은 운영용 인증이 아니다.
- 목록과 상세는 자기 회사 발주만 보여 준다. 다른 회사·없는 발주는 같은 404를 반환한다.
- B회사 대상 요청 장치는 결함 공간에만 있다. 실제 변경 확인은 B회사 관리자로 접속해 수행한다.

## 초기 데이터와 관찰

| 발주 | 회사 | 상태 | 승인 처리 횟수 |
|---|---|---|---:|
| 1001 | A | 승인 대기 | 0 |
| 1002 | A | 승인 완료 | 1 |
| 2001 | B | 승인 대기 | 0 |

- 횟수와 상태는 서버 DB에서 다시 읽는다. 요청 횟수나 성공 메시지 횟수가 아니다.
- 직접 승인 요청은 화면의 역할별 승인 버튼을 거치지 않는 관찰 장치다.
- 실제 서버 응답은 상태 코드와 본문을 함께 표시한다. 후속 조회가 이 응답을 덮어쓰지 않는다.
- 각 실습 전에 현재 공간을 초기화하고 시작 사용자를 선택한다.
- 초기화는 해당 공간의 데이터만 복원하고 그 공간의 모든 세션을 해제한다.
- 요청 처리 중 초기화는 409로 거부한다. 코드·의존성·다른 공간 데이터는 보존한다.
- 서버 재시작은 DB를 보존하지만 세션은 해제한다. 사용자를 다시 선택한다.
- 본 실습 시작본은 자기 회사 발주를 역할·상태 제한 없이 승인한다. 타회사·없는 발주는 404다.
- 역할 정책은 실습 1에서 질문을 찾은 뒤 확정하며 실습 2에서 독자 AI가 구현한다.
- 역할 실습까지만 마친 코드는 상태 제한이 없다. 상태 실습에서 승인 대기만 허용하도록 추가한다.
- 결함 공간은 역할·상태 검사가 있지만 회사 범위 조회만 빠진 비교 구현이다.
- 결함 공간의 관찰 절차와 기대 결과는 실습 4에서 확인한다. 실제 계정·데이터는 사용하지 않는다.
- 로그인하지 않은 승인 요청은 두 공간 모두 401이다.

## 실습 순서

원고 `04_chapter4.md`의 본문을 실습 안내와 프롬프트의 기준으로 삼는다.
본문을 따라 진행 중이면 `lessons/`를 별도로 실행하지 않는다.
키트만 사용하는 독자는 아래 순서로 `lessons/`를 읽는다. 대응하는 AI 프롬프트는 본문과 같다.

1. `lessons/01_requirement.md`: 조회 담당자의 승인 결과와 원문을 비교하고, 승인 역할을 결정하는 데 필요한 질문 하나와 이유를 적는다.
2. 질문 검토 후 `lessons/02_role.md`의 확정 답변을 읽고 역할 검사를 구현한다.
3. 역할 실습 완료 후 `lessons/03_state.md`에서 현재 상태 검사를 추가한다.
4. 상태 실습 완료 후 `lessons/04_company.md`에서 회사 경계 결함을 추적하고 최소 수정한다.

후속 자료의 정책을 첫 질문의 정답처럼 가져오지 않는다.
각 실습 전에는 현재 공간을 초기화하고 사용자를 다시 선택한다. 메뉴 열기와 상세 조회 후 승인한다.
초기화는 앞에서 구현한 코드를 되돌리지 않는다.
상태 실습의 구체적인 규칙과 기대 결과는 실습 3에서 확인한다.
상태·횟수는 같은 저장 경계에서 반영된다. 서버 재시작 후에는 사용자를 다시 선택해 조회한다.
두 공간의 코드를 복사하지 않는다. 결함 공간은 고정 역할·상태 검사로 독립 실행된다.
회사를 고친 뒤 초기화하고 타회사 거부·자기회사 정상 승인을 모두 확인한다.

python verify_observation.py

이 검사는 파일 변경만 확인한다. 승인 업무 규칙이나 브라우저 동작의 통과를 뜻하지 않는다.
실패를 통과시키려고 검사 도구·기준 데이터를 변경하지 않는다.

## 실습 4 완료 후 선택 API 검증

```powershell
.\.venv\Scripts\python.exe .\verify_business_rules.py
```

두 공간의 10개 조합과 쿼리·본문 회사 값 위조 2개씩, 총 24개 사례를 독립 초기 데이터로 실행한다.
현재 코드를 임시 폴더로 복사하고 별도 로컬 서버·DB·세션을 사용하므로 기존 .lab과 실행 중인 서버를 유지한다.
추가 패키지는 필요 없으며 start_lab.ps1에서 준비한 가상환경의 Python을 사용한다.
시작본·중간 단계는 완성 기준을 만족하지 않아 실패할 수 있다. 실습 4를 마친 뒤 실행한다.
RESULT의 Pass=24, Fail=0, Not Run=0과 종료 코드 0을 확인하면 전체 통과다.
FAIL은 첫 실패 행의 기대값·실제값·응답 형식을 비교하고, NOT RUN은 표시된 환경·DB·서버 오류를 확인한다.
종료 코드는 통과 0, 기준 실패 1, 환경·미실행 문제 2다. 문제를 고친 뒤 같은 명령으로 다시 검사한다.
서버 준비·정리 오류가 있으면 통과로 보지 않는다. 검사 기준을 바꿔 실패를 감추지 않는다.
이 도구는 화면 버튼 제한, 동시 요청이나 저장 실패 시험을 대신하지 않는다.
