# Chapter 11 — AI와 주문 승인 기능 완성하기

업무 조건을 설명하고 AI에게 구현과 실행을 맡긴 뒤, 화면에서 정상 승인과 재고 부족 결과를 확인합니다.

## 시작 위치

VS Code에서 이 `ch11/` 폴더를 엽니다. AI는 `AGENTS.md`와 `connection_spec.md`, 관련 하위 지침을 먼저 읽습니다.
백엔드는 `workspace/erp-project/`, 프론트엔드는 `workspace/frontend-project/`입니다.
Chapter 10 파일을 복사하지 않습니다. Day 00의 ERP 프로젝트는 이후 별도 폴더에서 준비합니다.

## 역할과 진행 순서

| 순서 | 독자 | AI |
|---|---|---|
| 준비 | 전용 DB 생성·연결값 로컬 설정 | 환경·연결 확인 |
| 구현 | 합의한 업무 조건으로 구현 요청 | SQL·API·화면 구현·DB 적용 |
| 실행 준비 | 미정 업무 조건이 있을 때 결정 | 별도 데이터로 자동 검사·서버 실행 |
| 정상 확인 | A 수량 1→3 입력·저장 후 승인·화면과 DB 대조 | 필요할 때 오류 조사 |
| 부족 확인 | B 수량 1→3 입력·저장 후 승인 요청·거절과 데이터 유지 확인 | 필요할 때 오류 조사 |
| 수정·마무리 | 기대와 실제 차이 설명·결과 판단 | 수정·관련 검사·코드 연결 설명 |

## 확인할 두 사례

| 사례 | 직접 입력·저장할 수량 | 시작 재고 | 기대 결과 |
|---|---:|---:|---|
| 정상 승인용 주문 A | 3 | 10 | 승인 완료·재고 7·원장 1건, 증감량 -3 |
| 재고 부족용 주문 B | 3 | 2 | 거절 사유·승인 대기·재고 2·원장 추가 없음 |

두 주문은 서로 다른 상품을 사용합니다. A에서 B로 넘어갈 때 초기화하지 않습니다.
시작 수량은 모두 1입니다. 각 주문의 수량을 3으로 바꿔 저장하고 새로고침으로 확인한 뒤 승인합니다.
수량 저장은 재고·원장·승인 상태를 바꾸지 않습니다. 재고보다 많은 수량도 저장하지만 승인할 때 부족하면 거절합니다.
미저장 입력이 있으면 승인할 수 없고, 승인 완료된 주문의 수량도 바꿀 수 없습니다.
AI의 자동 검사는 별도 데이터를 사용하고 독자가 쓸 두 주문은 시작 상태로 남깁니다.
직접 확인한 값은 독자가 기록합니다. AI가 예상값을 실제 관찰값으로 대신 작성하지 않습니다.

## 연결과 재개

- 연결값은 백엔드 로컬 `.env`에만 설정하고 대화·코드·로그로 공유하지 않습니다.
- 실행 도구와 서버가 로컬 설정을 사용합니다. AI는 전용 대상 확인 뒤 SQL 적용과 검사를 수행합니다.
- 전용 대상 확인이나 연결이 실패하면 AI가 실행 결과를 조사합니다. 다른 DB로 임의 변경하지 않습니다.
- 중단 후에는 AI에게 현재 SQL 적용·DB·서버 상태를 조사하고 이어서 진행하도록 요청합니다.
- 복습 데이터가 필요하면 해당 사례 재준비를 요청합니다. 기존 개인 작업이나 전체 DB를 초기화하지 않습니다.

## 결과가 다를 때

어떤 주문에서 무엇을 기대했고 실제로 무엇이 표시됐는지 AI에게 설명합니다.
AI가 화면·API·DB를 조사하고 수정한 뒤 관련 검사를 다시 실행하고 재실습을 준비합니다.
독자는 문제가 있던 상황을 다시 확인합니다.

## AI가 사용하는 실행 도구

아래 명령은 `workspace/erp-project/`에서 이 프로젝트의 Python으로 실행합니다.
Windows에서는 준비한 `venv/Scripts/python.exe`, macOS·Linux에서는 `venv/bin/python`을 사용합니다.
독자가 아래 명령을 모두 수동 실행하는 실습이 아니라 AI가 조사·실행할 도구 목록입니다.

| 명령 | 하는 일 |
|---|---|
| `python lab.py env` | Python·의존성·Node·프론트 의존성·로컬 설정 확인, DB에는 접속하지 않음 |
| `python lab.py init` | 전용 대상 대조 뒤 빈 시작 DB에 표식과 SQL 적용 이력 준비 |
| `python lab.py inspect` | 연결·표식·적용 이력 확인 |
| `python lab.py apply 파일명.sql` | 백엔드 `sql/`의 검토한 스키마 파일을 적용하고 해시·이력 기록 |
| `python lab.py prepare` | 없는 A·B를 수량 1로 준비, 기존 실습 결과는 보존 |
| `python lab.py state` | 두 주문의 상태·현재고·주문별 원장 건수와 증감량 조회 |
| `python lab.py prepare --case B --reset` | 재실습 요청을 받은 경우에만 B를 시작 상태로 복원 |
| `python lab.py servers start` | 두 서버 실행과 HTTP 응답 확인 |
| `python lab.py servers status` | 도구가 실행한 서버와 다른 프로세스의 포트 사용 구분 |
| `python lab.py servers logs` | 연결값을 가린 최근 서버 로그 확인 |
| `python lab.py servers stop` | 이 도구가 실행하고 현재 관리하는 서버만 종료 |
| `python lab.py resume` | 서버·SQL 적용 이력·두 주문 상태를 조회, 초기화·서버 재시작은 하지 않음 |
| `python verify_core.py` | 별도 데이터로 DB·HTTP 업무 검사와 프론트 빌드, A·B 보존 확인 |

서버 명령에는 `--service api` 또는 `--service web`을 붙여 한쪽만 다룰 수 있습니다.
서버 시작은 의존성 설치와 프론트 빌드를 대신하지 않습니다. AI는 제공된 requirements와 npm 잠금 파일로 설치하고 기존 빌드 명령을 실행합니다.

`verify_core.py`는 제공된 독립 검사이므로 기대값을 수정하지 않습니다. 필요한 검사만 실행할 때는 `--only db`, `--only http`, `--only build`를 사용합니다.
HTTP 검사는 필요하면 관리 대상 API를 실행하고 별도 검사 데이터를 만든 뒤 정리합니다. DB 검사는 전체 롤백으로 끝납니다.
직접 화면 확인과 여러 연결의 동시성 검사는 별도 범위입니다. 미실행 검사를 성공으로 보고하지 않습니다.

## 로컬 DB 대상 설정

`.env.example`을 참고해 `DATABASE_URL`과 `CH11_PROJECT_REF`를 로컬 `.env`에 설정합니다.
`CH11_PROJECT_REF`는 전용 Supabase 프로젝트의 20자리 참조 ID입니다. 연결 URL의 호스트 또는 Session pooler 사용자와 별도로 대조합니다.
DB 이름 `postgres`, 포트 5432의 직접 연결 또는 Session pooler만 받습니다. Transaction pooler와 TLS 비활성 설정은 거절합니다.
연결 뒤 실제 DB 이름·세션 사용자도 확인합니다. 이 검사는 프로젝트가 폐기 가능한 실습용이라는 독자의 확인을 대신하지 않습니다.
설정이나 검사가 실패하면 이유 코드만 표시하고 연결 URL·비밀번호·드라이버 예외 전문은 출력하지 않습니다.

최초 `init`은 기존 업무 객체가 없는 DB에서만 수행합니다. 이미 구현한 DB에서는 `inspect`와 `resume`으로 이어갑니다.
이전 표식만 있거나 개편 전 테이블이 있는 DB는 자동으로 채택·초기화하지 않습니다.
기존 `verify_lab.py`의 `direct`·`reset`·`shortage` 쓰기 명령은 차단하고 새 도구로 안내합니다.

## 현재 제공 상태

환경 확인·DB 적용·사례 준비·서버 실행·독립 업무 검사 도구가 제공됩니다. 기능은 AI 구현 요청으로 생성합니다.
현재 개인 코드를 새 명세의 완료 구현으로 판단하지 않습니다. 새 스키마가 없으면 해당 검사를 실행하지 않고 이유를 보고합니다.
기존 개인 실습 파일과 DB 결과는 보존하고 차이를 먼저 확인합니다. `.ch11-runtime/`의 서버 기록·로그는 배포하지 않습니다.
