# Chapter 11 연결 명세

## 적용 범위

이 문서는 개편된 ch11의 구현 목표다. 현재 원고·실행 도구·참조 코드가 모두 구현됐다는 뜻은 아니다.
현재 파일을 먼저 조사하고 아래 목표와 차이를 구분한다. 기존 개인 작업은 자동으로 덮어쓰지 않는다.
이 명세 자체는 독자의 기능 구현 중 수정하지 않는다.

## 함께 완성할 업무 결과

| 상황 | 동작 |
|---|---|
| 승인 전 수량 저장 | 양의 정수만 저장·DB 재조회, 재고·원장·승인 상태 유지 |
| 미저장 입력 | 승인 차단·수량 저장 안내 |
| 재고 충분 | 재고 차감·원장 기록·주문 승인 완료를 함께 저장 |
| 재고 부족 | 승인 거절·주문과 재고 및 원장 유지·사유 표시 |
| 저장 성공 | 저장 결과를 재조회해 승인 완료와 현재고 표시 |
| 이미 승인된 주문 | 서버에서 수량 변경·재처리 거절·추가 차감과 원장 중복 없음 |

AI는 구현·DB 적용·자동 검사·서버 실행을 맡고, 독자는 화면에서 정상·부족 두 사례를 판단한다.
트랜잭션과 재승인 방지는 필수 구현 조건이다. 두 화면 실험만으로 중간 실패·동시성까지 검증했다고 설명하지 않는다.

## 기존 기반과 구현 위치

- 백엔드는 `workspace/erp-project/`, 화면은 `workspace/frontend-project/`다.
- 기존 FastAPI·SQLAlchemy·psycopg2, Vue Options API·Axios와 의존성 잠금 파일을 사용한다.
- API의 시작 위치는 `api/main.py`, 화면은 `src/components/ApproveOrder.vue`와 `src/App.vue`다.
- 필요한 SQL은 백엔드 `sql/`에 파일로 저장한다. 스키마·데이터 준비·조회·재준비를 구분한다.
- 테스트와 실행 도구의 파일명·명령은 제공 파일을 조사한다. 아직 없는 도구를 존재하는 것처럼 안내하지 않는다.
- 새 프로젝트·CSS 라이브러리·인증·다른 업무 기능을 추가하지 않는다.

## DB 실행 기반의 완료 조건

- 독자가 전용 Supabase 프로젝트를 만들고 백엔드 로컬 `.env`에 연결값을 설정한다.
- 실행 도구와 서버는 `DATABASE_URL`을 내부에서 사용한다. 실제 값을 열거나 출력하는 절차는 만들지 않는다.
- 적용 전 로컬 설정의 전용 실습 대상 식별자와 실제 연결 대상을 대조한다. 식별 방식과 검사 명령은 실행 도구 정비에서 구현한다.
- 최초 준비는 위 대상 대조를 통과하고 예상하지 못한 기존 업무 객체가 없을 때만 ch11 표식을 만든다.
- 이후 쓰기 작업은 대상 대조와 `foundation_lab_marker`의 `chapter11` 표식을 함께 검사한다. 표식만으로 전용 DB라고 판단하지 않는다.
- 연결 대상이 불명확하거나 기존 객체가 명세와 다르면 중단한다. 임의 DROP·기존 데이터 삭제·자동 스키마 이전을 하지 않는다.
- SQL 파일은 실행 도구로 적용하고 적용 결과를 확인한다. 파일 존재를 DB 적용 성공으로 해석하지 않는다.
- 스키마 재적용은 기존 객체를 파괴하지 않아야 한다. 사례 재준비는 별도 명령으로 분리한다.
- 재실습 요청에서는 ch11의 지정 주문·상품·원장만 대상으로 한다. 다른 사례와 개인 데이터를 초기화하지 않는다.

## DB 구조의 목표

기존 이름과 자료형을 유지하고 표시 이름과 주문별 원장 조회 필드를 추가한다.
아래 구조는 새 시작 DB의 목표이며 기존 DB에 즉시 적용할 이전 절차가 아니다.

| 테이블 | 필드와 조건 |
|---|---|
| `stock` | `product_id VARCHAR(50)` PK, `product_name VARCHAR(100) NOT NULL`, `quantity INT NOT NULL DEFAULT 0 CHECK (quantity >= 0)` |
| `orders` | `order_id UUID` PK, `order_name VARCHAR(100) NOT NULL`, `product_id VARCHAR(50) NOT NULL` FK, `quantity INT NOT NULL CHECK (quantity > 0)`, `status VARCHAR(20) NOT NULL DEFAULT 'CREATED' CHECK (status IN ('CREATED','PAID'))` |
| `stock_ledger` | `ledger_id BIGSERIAL` PK, `order_id UUID NOT NULL` FK, `product_id VARCHAR(50) NOT NULL` FK, `qty_change INT NOT NULL`, `reason VARCHAR(100)` |

- FK는 `orders.product_id → stock.product_id`, `stock_ledger.order_id → orders.order_id`, `stock_ledger.product_id → stock.product_id`다.
- 세 테이블의 `corp_id VARCHAR(50) NOT NULL DEFAULT 'HQ'`를 유지한다. 회사 소속 기록이며 접근 제어가 아니다.
- `orders`와 `stock_ledger`의 `created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()`를 유지한다.
- 원장 조회는 `order_id`로 해당 주문에 한정한다. 상품 전체 원장이나 사유 문자열 검색을 주문별 검증으로 대신하지 않는다.

## 주문 승인 DB 함수

- 기존 호출 `approve_order(UUID, VARCHAR, INTEGER) RETURNS VOID`와 매개변수 `p_order_id`, `p_product_id`, `p_qty`를 유지한다.
- NULL·0 이하 수량, 주문 없음, 저장된 상품·수량과 불일치를 쓰기 전에 거절한다.
- 주문 행을 잠근 뒤 최신 상태가 `CREATED`인지 검사한다. `PAID`면 거절하고 어떤 데이터도 다시 쓰지 않는다.
- 상품 재고 행도 잠그고 최신 재고가 주문 수량 이상인지 검사한다. 부족하면 쓰기 없이 거절한다.
- 정상 처리에서는 재고 차감·주문을 참조하는 원장 `-수량` 기록·주문 `PAID` 변경을 같은 트랜잭션에서 수행한다.
- 함수 안에 별도 COMMIT을 넣거나 예외를 삼키지 않는다. 중간 실패 시 세 변경이 함께 취소돼야 한다.
- 화면 잠금은 서버 재승인 방지를 대신하지 않는다. 행 잠금만 있고 주문 상태 검사가 없는 구현도 완료가 아니다.

## API의 목표

- 수량 저장은 `POST /orders/quantity`, JSON은 `order_id` UUID·`qty` 1~2147483647의 정수다. 문자열·소수·bool·NULL·범위 밖 값은 `422`다.
- 수량 저장은 `change_order_quantity(UUID, INTEGER) RETURNS VOID`로 연결한다. 주문 행 잠금 뒤 존재·최신 `CREATED` 상태를 검사하고 `orders.quantity`만 바꾼다.
- 수량 저장으로 재고·원장·승인 상태를 바꾸지 않는다. 재고보다 많은 수량도 저장하며 재고 검사는 승인 시 수행한다.
- 이미 승인된 주문의 수량 변경은 `400`으로 거절한다. 승인과 수량 저장이 겹쳐도 같은 주문 행 잠금과 저장 수량 대조로 승인 후 변경·수량 불일치를 막는다.
- 수량 저장도 commit 성공 뒤 `200`과 `{"status":"success"}`를 반환하며, 오류·커밋 장애 처리는 승인과 같은 원칙을 따른다.
- 기존 승인 요청은 `POST /orders/approve`, JSON은 `order_id` UUID·`product_id` 문자열·`qty` 1 이상 정수다.
- 잘못된 UUID·양수가 아닌 수량은 요청 모델에서 `422`로 거절한다.
- SQLAlchemy·psycopg2 동기 호출에 맞춰 경로 함수는 일반 `def`로 작성하고 바인딩 매개변수를 사용한다.
- `commit()` 성공 뒤에만 `200`과 `{"status":"success"}`를 반환한다.
- 재고 부족·이미 승인됨 등 업무 거절은 기존 학습용 `400`과 비밀값이 없는 `detail`로 전달한다.
- 예상하지 못한 DB·연결 오류는 내부 예외 전문 대신 일반 오류로 알리고 성공 처리하지 않는다.
- 예외 시 rollback을 시도하고 요청별 세션을 닫는다. 커밋 중 장애는 결과가 미확인일 수 있으므로 저장 취소를 단정하지 않는다.
- 새 조회 요청은 `GET /orders`다. 독자용 두 주문을 `items` 배열로 반환한다.
- 각 항목은 `order_id`, `order_name`, `product_id`, `product_name`, `qty`, `current_stock`, `status`를 포함한다.
- `qty`는 저장된 `orders.quantity`, `current_stock`은 현재 `stock.quantity`, `status`는 저장된 주문 상태다.
- 조회 실패나 주문 누락을 시작 재고·가짜 주문으로 채우지 않는다. 화면이 오류·빈 결과를 구분하게 한다.
- 기본 API 주소는 `http://localhost:8000`, 화면 허용 출처는 `http://localhost:5173`이다.
- `/docs` 호출은 선택 실습이며 Core의 필수 단계로 만들지 않는다.

## 화면의 목표

- 조회한 주문 A·B를 이름으로 구분하고 상품명·주문 수량·현재고·저장된 주문 상태·승인 버튼을 표시한다.
- 저장된 주문 수량과 수정 중인 입력값을 구분한다. 이름표가 있는 수량 입력란과 별도 수량 저장 버튼을 제공한다.
- 수량은 양의 정수만 입력·저장하고 미저장·잘못된 입력이 있으면 승인하지 못하게 한다. 수량 저장·승인은 처리 중 추가 조작을 차단한다.
- 수량 저장 성공 뒤 DB를 재조회해 저장된 수량을 표시한다. 화면의 입력값만 저장 결과로 간주하지 않는다.
- 수량 저장 응답 유실·조회 실패도 결과 미확인 또는 저장 성공 후 조회 실패로 안내하고 승인·추가 수량 저장을 막은 채 재조회하게 한다.
- 승인 완료된 주문은 입력란·수량 저장·승인 버튼을 모두 잠근다.
- 긴 UUID를 독자가 복사하거나 입력하지 않는다. 조회된 식별자로 승인 요청을 보낸다.
- 로딩·빈 결과·조회 오류를 구분하고, 승인 처리 중 표시와 추가 클릭 차단을 제공한다.
- 성공 응답 뒤 주문 목록을 DB에서 재조회한다. 화면 재고를 직접 빼거나 성공 변수만 바꾸지 않는다.
- 승인 성공 후 재조회가 실패하면 저장은 성공했지만 최신 상태를 읽지 못했다고 알리고 재조회 경로를 제공한다.
- 부족 거절은 사유를 보여 주고 승인 완료로 바꾸지 않는다. 다음 요청 시 이전 오류를 지운다.
- 응답이 없으면 처리 결과 미확인으로 안내한다. 재조회로 상태를 확인하기 전 같은 승인을 무조건 재요청하지 않는다.
- 이미 승인된 주문은 새로고침 후에도 완료 상태로 표시하고 승인 버튼을 잠근다.
- 키보드 사용과 좁은 화면에서 정보·결과를 읽을 수 있어야 한다. 별도 검증 패널은 만들지 않는다.
- 기본 화면 주소는 `http://localhost:5173`이다. AI가 실제 실행·접속 결과를 확인한 뒤 주소를 보고한다.

## 독자용 두 사례

| 사례 | 주문 ID | 상품 ID | 표시 이름 | 수량 | 시작 재고 | 시작 상태 | 시작 원장 |
|---|---|---|---|---:|---:|---|---:|
| A | `00000000-0000-0000-0000-000000000001` | `PROD-100` | 정상 승인용 주문 A / 정상 확인용 상품 | 1 | 10 | `CREATED` | 0건 |
| B | `00000000-0000-0000-0000-000000000002` | `PROD-200` | 재고 부족용 주문 B / 부족 확인용 상품 | 1 | 2 | `CREATED` | 0건 |

- 위 표의 수량은 시작 수량이다. 독자가 A와 B를 각각 3으로 바꾸고 저장·새로고침으로 유지됨을 확인한 뒤 승인한다.
- 수량 저장 직후에는 수량만 3이고 각 주문의 시작 재고·`CREATED`·원장 0건이 유지돼야 한다.
- A 승인 후 `PAID`·재고 7·원장 1건과 증감량 `-3`을 확인한다.
- B 요청 후 재고 부족 사유·`CREATED`·재고 2·원장 0건을 확인한다.
- 두 사례 사이에는 초기화하지 않는다. 각 상품이 달라 서로 재고에 영향을 주지 않는다.
- 제공 조회 SQL 하나로 두 주문의 이름·저장 수량·상태·현재고·주문별 원장 건수·증감량을 한 표에서 대조한다.
- 원장 없음은 건수 0으로 구분하고 원장 행이 없다는 사실을 증감량 0 한 값으로 숨기지 않는다.
- 반복 실습 데이터는 AI가 해당 사례만 재준비한다. 수동 초기화 SQL은 도움말로 둔다.

## 검사·실행·재개 완료 기준

- 정상·부족·재승인·중간 실패·조회·HTTP 검사는 별도 테스트 주문·상품을 사용한다.
- 수량 1→3 저장·잘못된 입력 거절·재고 초과 수량 저장·승인 후 수량 변경 거절도 별도 데이터로 검사한다. 조회 검사는 독자 수량을 1이나 3으로 고정하지 않고 현재 DB 값과 대조한다.
- 자동 검사 종료 뒤 독자용 A·B는 시작 상태로 유지한다. 기존 독자 결과가 있으면 재준비 요청 없이 지우지 않는다.
- 빌드와 서버 실행을 수행하고 실제 응답을 확인한다. 포트 충돌 시 다른 프로세스를 임의 종료하지 않는다.
- 재개 시 적용된 SQL·DB 상태·서버 상태를 조사하고 필요한 작업만 이어간다. 시작부터 재설치·초기화하지 않는다.
- 관련 검사 실행 결과와 DB 적용 결과를 구분한다. 브라우저 확인·동시성·응답 유실 등 미실행 범위는 명시한다.
- 완료 보고는 구현 결과·DB 적용·검사 결과·실제 화면 주소·남은 문제로 제한한다.
- 독자의 관찰값은 대신 작성하지 않는다. 결과가 다르면 원인을 조사하고 수정·관련 검사·재실습 준비를 수행한다.
